## Owner and current mechanism

### Authorization boundaries between project root and associated root

[The composition root](../../apps/serve/service/bootstrap.py) uniquely resolves the new project workspace root: the product `workspace_root` setting takes precedence over `SCHOLARSEED_DEFAULT_WORKSPACE`, and then takes the cwd or process cwd passed in by the caller. The launcher and Content must not independently infer the root path; the registry and actual root of an existing project cannot be re-guessed from the directory name. For path and database ownership, see [Persistence Boundary](../architecture/persistence.md).

[ContentPort](../../apps/serve/service/platform/content.py) is responsible for the cross-domain path contract. [ProjectSpace](../../apps/serve/service/content/service/space.py) parses the project or mount path and reviews the ownership, rejecting paths outside the allowed root and nested paths beneath a file mount; the string prefix is not an authorization check. This parsing step does not replace the atomic safety boundaries of file operations, nor does it demonstrate acceptance of Windows reparse-point or concurrent replacement.

[Associated root Owner](../../apps/serve/service/content/service/roots.py) verifies project ownership, retains soft revocation records, and generates a writable root collection from the current effective root; the combined root injects this capability into the session domain and does not require the session domain to import Content in the reverse direction. [Codex Adapter](../../packages/adapters/codex/scholarseed_codex/permission.py) owns the current `sandboxPolicy` translation. In `workspace-write` mode, the policy combines the working directory with explicitly provided roots; the read-only and full-access branches differ. The old damoagent host is no longer the current owner. When Windows provides a currently authorized writable root, the reuse platform storage capability preserves the current host user’s inheritable access to child paths so that Serve can read the products created by the sandbox; the root collection is not expanded or authorized to other principals, and the collection is not provided when initialization fails. Permission initialization is not performed for unregistered or unavailable projects. This initialization does not recursively rewrite the protected history child DACL; the old copy will not automatically become readable if inheritance has been disabled. Such recovery should be handled by a well-scoped data recovery process that does not authorize recursively when a Review read fails. Deregistration, next round policy update, and running process permissions are different final states; soft deregistration or interrupt request return cannot be declared as immediate deprivation of write permissions of the running OS.

Real authorization acceptance must prove all three outcomes: an authorized root is writable, an unauthorized root is denied, and a new turn is denied after revocation. Negative examples must avoid temporary directories that may be allowed by the sandbox by default, and check the implicit allowed range of the actual version. Successful writing of `$TMPDIR` cannot be used to infer that explicit authorization has expired. True turn reports of historical versions are not proof that the current adapter, platform, or migration process has passed.

This is the coverage boundary to be verified by the Owner. It does not prove that the user problem has been reproduced. It does not authorize modification of the database, modification of universal equality semantics, or product modification in knowledge governance. Changes must be accepted separately by source bytes, annotations are saved in real time, old history is retained, restored, and copies are exported explicitly. Documents cannot be used to claim that all isolation has been passed.

## Review draft, revision submission and withdrawal boundaries

[ReviewDraftStore](../../apps/desktop/src/renderer/src/features/resources/draft.ts) Press project/batch/file to save temporary decisions and review, pending, candidate, and expected disk revision; the editing bytes are still held by the original workspace session, and no second set of editors or server-side variable draft libraries are added. It is not proof of disk CAS or submission success, completion is still judged by the Serve receipt.

The failure protection of hydrate is not equal to the submission refresh protection: currently `submitBatch` directly calls `choose` as a new member after getting refreshed, retains the old action/expectedDiskRevision, and then `decisions` reads the complete vector after rebinding; there is no failure check of hydrate called here. Cannot commit subsequent revisions that the user has never seen are still review invariants; whether refresh/rechoose maintains this is subject to independent behavioral verification. Subsequent Serve CAS/recoveries may still reject, and coverage cannot be asserted, nor can the joint be proven safe with a pure draft test.

For a dirty member marked for revision, ReviewBatch collects bytes through `reviewDraftBytes`. It refreshes the batch, builds a complete decision vector, and sends `revised_content` with the decision to the batch API; it does not call the ordinary save API for each member before submission, as the old design proposed. Serve backs up the current content during batch application, calls `commit_working` with the expected revision, and then applies the review decision. This operation may have its own recovery state. A single HTTP request does not make writes across files atomic; on failure, recovery and error reporting remain the responsibility of the existing owner.

Choosing accept/reject/revise is not the same as revoke. Undo the read-first current revision: the disk has deviated from the candidate or the expected revision of the previous revise is different, `restore_candidate` will be pre-checked and called to restore coordination; dirty memory still needs to be discarded/synchronized by the original workspace. Therefore, one cannot generalize all undos to purely memory operations, or assume that closing a tag undoes disk side effects. True verification requires checking restored backups, new entries added during the period, and late results, rather than just selecting clear.

The left side of text comparison is base; the right side is selected as accept candidate, reject base, or dirty session text/current disk content. The old “always base → current” description does not apply to all states. Fixed review base and historical Version associations are also not interchangeable; reading three contents does not authorize skipping file identity, revision, or recovery verification.

[VersionStore](../../apps/serve/service/resources/persistence/version.py)'s `finalize_review` fixes the complete `SnapshotIdentity` before modification: text object, existence state, path, permission semantics, and annotation object. `base_version_id` is only a historical association, while `base_origin` retains the prior pending source. Rejection through `_cancel_pending` uses the exact `review.base` and verifies the identity before restoring it; it does not use the latest Version. Ordinary discard without review instead uses the latest Version and reprojects through `sync_working`. User input that has not been archived before modification must be protected, and rejecting a review must not be treated as ordinary discard. The old requirement to “avoid creating a new Version while keeping the user's existing changes pending” is not a current guarantee: `commit_restore` may conditionally seal the base when restoring a base that differs from the latest Version. External changes may also create a review backup, and preserving old history during migration may produce an ordinary pending state after recovery. Verify sealing and pending outcomes separately, and bring any differences from the old requirements to the Owner.

`live_object_ids` uses the pending and batch members' base/candidate text and comments as strong references for garbage collection. Retention also preserves `base_version_id` while a review is open, so a baseline needed for review or dependency rejection is not collected prematurely. The [restore owner](../../apps/serve/service/resources/service/recovery.py) rechecks the target before resuming an apply: it continues only when the target records that the operation was applied, including partial or relocated states; other conflicts enter `NEEDS_ATTENTION`, with no blind overwrite. For migration that retains historical assets, see [Persistence Boundary](../architecture/persistence.md#旧审阅数据读取不等于恢复旧运行-owner). These branches do not establish full recovery or platform acceptance, and macOS/POSIX permission results cannot be extrapolated to Windows.

[Turn admission](../../apps/serve/service/chat/service/turns.py) is decoupled from file review decisions: open, failed, or application review batches in the project do not block the same session, new session, queue sending, or failed resending; the presence of unsaved content in the review editor does not become a conversation admission condition. Send does not query review status and does not automatically accept, reject, or clear old reviews. Explicit review decisions are still handled by the Resources Owner; pre-round baseline collection, file revision conflicts, and recovery verification are retained, and errors are still clearly reported when real resource operations fail. See [draft.test.ts](../../apps/desktop/src/renderer/src/features/resources/draft.test.ts) for related draft-only tests; they do not verify actual Office serialization, submit CAS, undo disk operations, or actual next-round admissions.

When the disk deviates from the candidate during the review period, the new round captures its own pre-modification baseline with the current stable disk content, without advancing the work head, modifying the record to be reviewed, or automatically sealing the version. No new file candidates will be generated when chatting only and the file remains unchanged. [Serve PDF platform](../../apps/serve/service/platform/pdf.py) uses narrow capabilities to unify structure, layout, coordinates and rendering, and does not move document identifiers, reference paragraphs, business access or AI actions into universal PDF services. The current dependencies are pypdf, pdfplumber, and pypdfium2; the product adopts this split to reduce coupling of license, geometry, and rendering responsibilities. Third-party licensing and distribution notices must still verify the actual locking dependencies and build products. Compliance acceptance cannot be inferred from the license name or source code import listed in the proposal.

PDFium render output is normalized to RGB. Verify the normalized viewer, CropBox, rotation, and text-layout coordinates against the same page. Text extraction alone does not prove correct selection hashes, double-column/CJK handling, chart exclusion, or citation navigation. [Extracted version](../../apps/serve/service/workbench/service/extraction.py) and [materialized version](../../apps/serve/service/workbench/service/materialize.py) are part of cache identity. Algorithm changes require old keys to be invalidated and rebuilt; do not reuse old geometry caches and claim behavior is unchanged. The independent product Skill owns its PDF capabilities and must not import Serve platform modules in the reverse direction.

`embedded_pdf_records` verifies the size, codec, and page number of the unique `scholarseed-annotations.json` and merges standard PDF reading annotations. Existing records are only backfilled to identify native sources; embedded records are not replayed to overwrite edits. Invalid embedded records are ignored with a warning while independent valid native annotations continue to be parsed; invalid containers return no records. Source descriptions are stored with each record to prevent resurrection after deletion and duplicate display/export. See [PDF Geometry and Record Boundaries](pdf.md) for details. Container admission remains with its owner. Validate annotation export/reimport and screenshots. Source migration does not replace wheel/Skill package closure or actual acceptance on each platform.

### PDF automatic area and authoritative cropping

[The region manifest](../../apps/serve/service/workbench/service/regions.py) is indexed by Workbench; Renderer must not add a separate detector. Revision, extractor version, page, kind, and normalized quad contribute to the region ID. The manifest also declares the coordinate space and unavailable pages. [The extractor](../../apps/serve/service/workbench/service/extraction.py) creates interactive Regions and Omissions for excluded text. A formula being interactive does not mean its text should be omitted. Detection uses auditable signals, not a probability or guarantee of 100% recall; manual selection remains a fallback for missed detections.

Project files and literature attachments keep their own read and admission paths; a generic raw-file interface must not bypass resource identity. An automatic crop request submits the source revision, page, and region ID. The server re-resolves the region from that document’s index and generates a PNG from the original PDF bytes; it does not accept a client-substituted quad for an automatic region. Manual selection uses restricted coordinates and automatic regions use their own identity; do not merge them into an automatic-coordinate fallback for compatibility. The project route currently checks the revision from a snapshot and then calls `read_bytes` separately. This does not prove that the two reads are race-free or that the crop is atomically bound to the revision.

Explanation and LaTeX transcription require an explicit action. Hovering does not authorize a model call, and transcription does not prove a claim in the paper. The system clipboard reuses Electron’s existing capability; a visible canvas or DPR is not an authoritative screenshot source. The region overlay must preserve text selection, scrolling, links, and annotations; verify buttons and keyboard focus separately, since source styles do not prove those interactions work. Source enrichment and compilation of untrusted TeX are outside the current local-detection implementation. Do not download sources, execute TeX, or change authorization to improve recall. Verify revision changes, missing regions, unavailable pages, rotation, double columns/CJK, copying, and real multimodal actions separately; an old implementation status is not retroactive acceptance evidence.

### Request life cycle of chart interpretation

[Literature Figure](../../apps/serve/service/literature/service/figure.py) retains the authoritative PDF source, revision, region, and crop for compilation. It uses the shared AssistantActionService for one-off model actions; PDF input is not forced into the text Resource domain. On success, the terminal path reads the source hash again and rejects a result if the source changed. The user prompt is a constrained request and cannot rewrite the source or security rules.

[Figure API](../../apps/serve/service/literature/api/analysis.py) first checks image capability and prepares the request. In the same POST SSE stream, it emits `prepared` and the crop before handing off to the shared `action_stream`. `prepared` does not mean model success; deltas are temporary previews, and later actions such as copying must use the complete terminal output. Figure analysis does not use the old long-task submission path, while full-text interpretation and translation still have separate long-task mechanisms. The one-off stream does not imply that all PDF background tasks can be cancelled.

Cancellation must check owner and invocation; aborting fetch does not prove that the upstream has stopped, and late output cannot cover the new selection or the switched document. Real verification includes persistence of personalized prompt words, first paragraph during generation, complete final state copy, cancellation/immediate reframe, and replacement source during generation, respectively verifying the input identity, event, and interface. [Graph flow contract](../../apps/serve/tests/contract_figure_stream.py) is a directional entry that does not include protocol fixtures, history screenshots, or HTTP 200 when real multimodal model calls and cancel final state proofs.
