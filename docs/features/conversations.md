# Project Session Isolation, History Search, and Current Object References

Read this page when changing project switching, session search or result navigation, or automatic references. For text selection and attachment sources, see [Selection Knowledge](selections.md); for file review and saving, see [Resources and Version Knowledge](resources.md). This page distinguishes current mechanisms, requirements that must remain, and real-acceptance gaps. It does not restore paths or status tables from old implementation plans.

<a id="当前-owner-与必要约束"></a>
## Current Owners and Required Constraints

[The product Store](../../apps/desktop/src/renderer/src/store.tsx) uses `selectProject` as the unified project selector. It first remembers the session in the original scope, resets the assistant's foreground scope when switching projects, and then restores the target project's own session. Therefore, the old plan's claim that “the target project has no foreground session” is no longer true. The required invariant is that a session from the old project must not leak into the new project; foreground navigation must not interrupt or delete background tasks. When changing this flow, verify the actual identity of the original thread and target scope; identical paths or visible labels do not establish session ownership.

The `list` method in the [session service](../../apps/serve/service/chat/service/sessions.py) first obtains records within the principal/runtime/scope boundary through the access Owner. Project scopes also validate workspace eligibility before matching the query. Query length, list limits, and hit projection belong to the service Owner. Do not scan all history and filter only in the Renderer, or bypass principal/project authorization for faster search. The old reason for “not creating a separate full-text index yet” was to reduce index consistency, migration, and recovery complexity. Whether to change indexing should be decided from real scale evidence; this is not a permanent prohibition. The list's total and bounded match results are separate; do not infer an exact hit total from field names.

### Display Relationships, Persistent Order, and Pinning

The [session catalog](../../apps/serve/service/chat/persistence/catalog.py) owns display-parent relationships and display order. They must not replace actual fork origins, message history, or frozen anchors. Moving a child session out changes only its display relationship and display-order namespace; it does not cross projects, delete source data, or fabricate ordering from business activity time.

The project catalog must assemble complete display groups within principal, runtime, project, and archive boundaries before applying persistent order and pagination to root groups and siblings. Siblings without manual ordering remain sorted by activity. Once manually ordered, activity must not overwrite the saved order. New and detached sessions enter the front of their partition. Pinning prioritizes the group in the view: pinning any member moves the whole group into the pinned area, while each row retains its existing pin value; a display group must not be split into duplicate copies. Relative moves accept only a sibling target and a before/after position. A top-level operation does not implicitly change pinning or reparent the session.

[Project Navigation](../../apps/desktop/src/renderer/src/features/project/Navigation.tsx) reuses [complete paginated reads](../../apps/desktop/src/renderer/src/api.ts). It must not process only the first 500 entries or send the current slice to the server as a complete replacement order. If concurrent archive/deletion removes a cursor anchor, that cursor must be explicitly invalidated. The client discards the partial catalog and performs at most one full reload; repeated invalidation returns a load failure instead of silently truncating the list with a successful empty page. Failure feedback distinguishes an unconfirmed result, and modifications are not blindly resent. Dragging and the equivalent keyboard menu action share authorization, sibling validation, and deduplication paths. Success does not force a switch to the current session.

Dragging a child up or down within its parent's content area reorders it. Dropping it on an existing root row, the root-level indentation area, or blank space at the end of the list only removes its display-parent relationship. It becomes an independent session at the front of the applicable partition and does not reparent any other child. Detaching uses the list drop target; there is no dedicated drop zone, and starting a drag does not change the source row's geometry.

Changes must verify the complete sibling transaction, pagination beyond 500 entries and cursor invalidation, unchanged business fields, incremental migration, late project responses, and real drag/keyboard use, order after activity, persistence after reopening, and exact navigation to the actual source. Component regression and catalog contracts do not replace real Desktop screenshots and runtime evidence from the final revision.

### Tab Navigation Must Not Write Back a Stale Composer Draft

The [product Store](../../apps/desktop/src/renderer/src/store.tsx) keeps the Composer draft in a separately subscribed state. Only a patch that explicitly includes `composerText` updates it. [Tab activation](../../apps/desktop/src/renderer/src/shell/TabBar.tsx) and [first-launch storage onboarding dismissal](../../apps/desktop/src/renderer/src/components/business/StorageFirstLaunch.tsx) submit only the fields they own. They must not spread a previously read, entire `AppState`, because stale `composerText` would overwrite text the user just entered. When changing navigation, check the [Store contract](../../apps/desktop/src/renderer/src/store.test.ts) and actual input behavior on the same tab, across tabs, and after returning home. Screenshots from old tasks do not prove that the current draft cannot regress.

The [AI panel](../../apps/desktop/src/renderer/src/features/assistant/AiPanel.tsx) resolves the current assistant project from the product Store. ### Recovery Wait After Completion and Consecutive Sends

Between a completion event and backend cleanup, a completed session may temporarily report `recovery_pending`. The send guard must not clear this flag on its own. The [Desktop catalog refresh policy](../../apps/desktop/src/renderer/src/catalog.ts) keeps refreshing while any loaded thread is awaiting recovery. The [session-state projection](../../apps/desktop/src/renderer/src/live.ts) updates the flag from authoritative server responses; sending is allowed again only after the flag clears. This does not trigger extra refreshes for ordinary idle threads. A successful screenshot of one turn does not prove that the same session can send continuously. When changing this behavior, check the [catalog contract](../../apps/desktop/src/renderer/src/catalog.test.ts) and real consecutive first and second turns followed by a sendable third turn. Do not hide a timing problem by disabling recovery protection.

The [AI panel](../../apps/desktop/src/renderer/src/features/assistant/AiPanel.tsx) restores navigation using the query, matching excerpt, and stable turn/item identifiers. Search results alone do not prove that navigation succeeds after history loads. When the Store loads session context, it patches by revision, removes automatic references with `origin=current_document`, and checks the current `activeSession` before writing back. The invariant is that an automatic object reference cannot reappear across sessions and explicit references are not removed with it. A cleanup call alone does not prove successful cleanup when there is a concurrent update or server conflict.

### The Focused Document Is This Turn's Scope, Not a Persistent Reference or Full Text

The `activeDocumentForTurn` sample in the [Store](../../apps/desktop/src/renderer/src/store.tsx) requires the displayed tab to equal `focusedTabId` and the source to be ready. Literature visibility follows the tab's actual `navigationView`; literature can be read in a project file view or the literature library. Project files still require the project-files view and must belong to the assistant's project. The scope does not include every open tab or a stale focus left behind after leaving the workbench.

At the send boundary, the [Composer](../../apps/desktop/src/renderer/src/components/business/Composer.tsx) saves the identity and submits it for admission with the client user message. Asynchronous session creation, queueing, or retries must not resample a different file. A literature identity includes the actual attachment ID; it does not default to the primary attachment.

When a client turn ID is reused, [Assistant freeze](../../apps/serve/service/assistant/service/context.py) compares the original question, selection revision, active identity, and selected-literature set. Reusing an ID must not replace the material. The active object enters the snapshot as a `NEXT_TURN` scope item without changing explicit selections. If source resolution fails, retain the unavailable item and reason; do not silently fall back to an old document or promise that the model can read the full text.

The [Content resolver](../../apps/serve/service/content/service/context.py) validates relative file locations against the server-side session project; the current active identity has an empty source revision. The [Literature resolver](../../apps/serve/service/literature/service/context.py) validates the project/global literature view and the specific attachment, carrying the attachment revision. This lightweight scope excludes unsaved edit buffers and does not mean that the source text was read or its bytes frozen. Later reads, full-text consent, and citations continue through their respective source and Bridge gates. Window visibility or the model knowing a name must not expand file permissions.

When changing this behavior, check the [context contract](../../apps/serve/tests/contract_assistant_context.py) and actual Composer, queue, and source consumers. Real product coverage should include tab switching, asynchronous session creation, identity conflicts on retry, non-primary attachments, disconnected sources, and no leakage into the next turn. Current call sites and old screenshots do not prove all these paths have passed acceptance.

### A User Question Is a Callback to the Original Session, Not a New Turn

The [HIL projection](../../apps/desktop/src/renderer/src/hil.ts) retains durable interaction facts in the conversation, with pending controls placed in the Composer dock. A resolved question with an answer becomes `interaction_reply`; a terminal result without an answer retains its causal position. Do not describe the old globally centered question-dialog design as the current UI, or present cancellation, stale, or unknown outcomes as user answers or ordinary sent messages.

Submission must use the original `session_id` and `request_id`; page or active-session switching must not redirect it. The [Serve inbox](../../apps/serve/service/chat/service/sessions.py) filters pending interactions by principal and live session. It currently also includes browser approvals, so do not repeat the old assertion that it contains only questions. [Native resolved consumption](../../apps/serve/service/chat/runtime/live.py) creates a snapshot from the catalog's confirmation record and preserves the decision's answers; an Adapter summary does not overwrite them. An inbox endpoint existing does not prove that the current UI consumes it. Verify global discovery, card placement, and server callbacks separately.

If the service returns `hil_response_not_retryable` or `hil_request_stale`, do not silently resend. Resolving the callback is not a terminal turn result, and Runtime may continue after a permission denial. Regression coverage must include ownership across pages/sessions, duplicate submissions, unknown results, cancellation, late confirmation, and history replay. Old success screenshots do not count as current acceptance.

### Per-Page Literature Evidence and Review Checkpoints

The [literature read contract](../../apps/serve/service/platform/bridge.py) limits reads to a contiguous, one-based page range with a per-request maximum. The [Evidence Owner](../../apps/serve/service/literature/service/evidence.py) verifies project association, the actual attachment, and content revision before reusing PDF indexing and citation Owners. A summary or PaperCard excerpt discovered in a catalog is not evidence that the original text was cited; a global discovery hit does not grant project read access. Metadata returned by a service, server-side byte reads, and full text visible to a model are different. Current gaps and consent scope are documented in [Full-Text Authorization](downloads.md#全文同意与有效授权范围); do not maintain a second gate here.

[Review publication](../../apps/serve/service/literature/api/review.py) reads the real artifact and binds it to the active session/turn, task workspace/run, and named checkpoint hash. A card is only a projection; it does not run another research engine or rerun an old session. The [report adapter](../../apps/serve/service/literature/service/review.py) distinguishes generation state, check criteria, and missing-evidence warnings. The existence of a report or a PASS result does not prove that current full-text citations and rendering were verified. Opening the original file and replaying a card are separate actions.

[Interaction contribution](../../apps/desktop/src/renderer/src/features/literature/interaction.ts) matches named business questions and presents a direct decision. Both current allow and deny responses use `respond`; do not repeat the old proposal's claim that the deny button necessarily interrupts directly. Denial or an unknown result does not grant full-text access. Whether later tools stop must be determined from actual policy and execution evidence. Do not substitute a Chinese header for server-side task, candidate, and HIL binding, or generalize one approval into permanent authorization for all later research stages.

The session's project identity and the project selected on the page are not the same fact. A global session has no project binding, so do not silently fall back to a default project to show resource candidates. `citation_document` in [Content context](../../apps/serve/service/content/service/context.py) explicitly rejects a missing project. Resources, literature, and history sources are validated according to their own declarations and session context. UI hiding does not replace server-side eligibility checks, and this rule does not warrant creating another session type or migrating historical data.

The `_project` method in [result saving](../../apps/serve/service/assistant/service/resources.py) checks that an explicit target matches the existing project for project sessions; a global session must specify a registered target. Saving a copy does not change the original session scope. The existence of a lower-level rebinding primitive does not prove approval to restore a user-visible migration entry point. When changing source or save behavior, separately validate global/project sessions, empty targets, wrong projects, page switching, and cold recovery.

## Assess Structured Plans and Execution Results Separately

[Adapter turn](../../packages/adapters/codex/scholarseed_codex/turn.py) converts native `turn/plan/updated` events into structured steps; a natural-language plan or text delta does not prove that a step ran. [SessionPlans](../../apps/serve/service/chat/service/plan.py) coordinates product-plan publication and native snapshots, events, and catalog persistence. Do not simplify current multi-source coordination to the old “Codex is the only source of truth” claim. Steps, turn identity, and event sequence numbers remain distinct; do not create another task database or parse progress from answer text. If an explicit declared tree already exists, a native snapshot without parent identity cannot overwrite it. A native method queries the current plan source in the same transaction and saves permitted events together with the catalog snapshot.

The [AiPanel](../../apps/desktop/src/renderer/src/features/assistant/AiPanel.tsx) mounts a compact, current-turn-only TodoPanel in the Composer header. The [todo projection](../../apps/desktop/src/renderer/src/todo.ts) maintains plan snapshots by sequence number and distinguishes the released source. A terminal event must not automatically check off unfinished steps, and a historical plan must not activate an unrelated later turn. The number of completed steps is not a duration percentage or proof of a real read. Snapshot history exists now, so do not carry forward the old assertion that “only the latest snapshot” is available. Events, durable recovery, display across turns, and real notifications require separate acceptance; a profile declaring `PLAN_SNAPSHOT` is not runtime evidence.

Plan totals and measured step durations come from execution intervals, not sums of child-step values; parent/child or parallel intervals may overlap. Show a step duration only when it has an independent `in_progress` snapshot interval. If independent timing evidence is missing, leave it blank. Do not present a shared time limit as measured, or show a less-than-or-equal sign, limit label, placeholder, or padded zero. Preserve the original milliseconds, display precision, and wait-time subtraction; do not apportion parent duration to fabricate unknown child durations.

**Current behavior**: `complete` atomically closes started leaves and leaves whose start was not recorded, using nonempty completion evidence. The latter are recorded in `reconciled_ids`; no `started_ids` or execution duration is fabricated. Existing strict `finish` and `reconcile` boundaries remain. Serve persists the exact targets of rejected start or completion requests. It publishes `resolved_tool_ids` only when a successful, newer-version receipt for the same turn and plan confirms that the original start target actually started or all original completion targets completed. Reconciled completion cannot stand in for a real start. Desktop shares this recovery association between live and historical projections, displays “已恢复”, and retains the original failure and technical details. The execution summary displays only the authoritative turn lifecycle: “进行中” while running, “已完成” after normal completion, “失败” after failure, “已中断” after interruption, and “结果待确认” when unknown or before an authoritative turn result is available. Historical tool failures, recovery attempts, and unchecked plans do not override the summary of a successful turn; they remain in their own details. An artifact or success text from the model does not replace a terminal turn result.

A read-only `get` rejected for invalid arguments is recovered only by a later genuine successful `get` in the same turn; a read receipt cannot recover a failed write. A rejected structural change is recovered only when an authoritative result for the same turn and plan, at a newer version, fully satisfies the requested ordered node tree and source. `create` and `release` also require their corresponding operation to have succeeded. Historical replay can reconstruct the same association from exactly matching durable tool-start and completion events plus bounded product receipts, without rewriting logs or databases. HTTP history and SSE, including mid-stream resume, share the projection. Runtime, native thread, turn, and tool identities must match. Missing, truncated, unknown, or authorization errors are never guessed into a recovery.

The workflow GET in the [settings API](../../apps/serve/service/chat/api/settings.py) returns `enabled=false`, `available=false`; POST also explicitly rejects the request. The old settings service can still read and write defaults, but that does not mean the public entry point or runtime supports workflows. Nor can capability be inferred from an old proposal's active status.

The retired custom Harness's Workflow PolicyRule priority table and Git pre-image checkpoint are not current public Runtime mechanisms. Session recovery, vendor file events, resource-version recovery, and file rewind are different capabilities. A successful session recovery does not mean that files in the user's workspace were rolled back. If file rewind is introduced later, it still needs an explicit definition of attributable write scope, protection against external-edit conflicts, and recovery consistency. Do not restore whole-workspace snapshots or use an old plan to authorize deleting user data; enabling workflows does not authorize skipping approvals. New capabilities must define and verify contracts in the actual Provider/Session, Adapter, and Serve Owners. This page records current limitations; it does not approve rebuilding the old Harness or treating historical acceptance as current product evidence.

### Answer Annotation Identity, Scope, and Context Enqueueing

The same selection may still be in a changed answer body. Binding to the full revision remains a required safety goal; the field's existence does not mean it is enforced. Changing product validation requires separate authorization and acceptance. Test a changed whole answer with an unchanged selection, non-BMP characters, out-of-range offsets, summary mismatch, same-session identity, annotation/enqueue transaction, and recovery separately. Validation should cover both paths, mixed numbering, invalidated sources, and cold recovery. Projection tests alone do not prove real reads, workbench navigation, or screenshot acceptance. Historical answers are not backfilled or rewritten based on old plans.

## Next-Turn Queueing, Current-Turn Steering, and Isolated Invocations

The message queue holds frozen input. Scheduling the next turn is different from an explicit user-requested steer of the current turn. TurnService scheduling, under `lifecycle_lock`, rejects running/stopping/terminated states, unknown outcomes, pending settlement, and incomplete resource admission. Any `submitting` or `outcome_unknown` row also blocks continuation. By default, only the head `queued` item is scheduled; failed items are not skipped. The existence of a resource-admission task does not mean that a native turn started. Only `COMPLETED` on the normal-result path triggers the next item; a change in `interrupt_generation` is handled as an interruption.

Steering uses the original queued body and checks the active Assistant revision/snapshot. On success, it records an independent client-message identity with `origin=steer` and binds it to the current native turn; it does not create a next-turn identity. An unknown receipt remains uncertain and must not be inferred as success from the send-button response or the end of a wait. Validation should separately cover admission wait, stop races, HIL, a failed queue head, late steer, and history recovery. Independent Agent Invocation uses the [Serve narrow protocol](../architecture/serve.md#invocation-配套接口与消费终态), not the Chat queue or direct model translation. Local cleanup after a disconnected stream does not prove that the vendor process exited.

### Permission Failure While Reading the Resource Baseline

When reading the queued turn's resource baseline encounters a permission denial, [TurnService](../../apps/serve/service/chat/service/turns.py) returns `resource_baseline_permission_denied` and a safe project-relative path. Other baseline failures use a separate generic code. A queue failure does not mean a native model turn has started. The [Desktop queue projection](../../apps/desktop/src/renderer/src/queue.ts) displays an actionable reason and path for the named code without exposing an absolute system exception path or raw credentials. After fixing access, the user must explicitly retry; changing the text must not bypass Content authorization. Check the [turn contract](../../apps/serve/tests/contract_assistant_turn.py) and [queue projection contract](../../apps/desktop/src/renderer/src/queue.test.ts). Real acceptance should show the same session rejecting a send first and succeeding after permission is restored. An old macOS screenshot is not current Windows acceptance.

## Unknown Queue Submission and Local Pending Copies

Queue reconciliation belongs to [TurnService](../../apps/serve/service/chat/service/turns.py). The Desktop [outbox](../../apps/desktop/src/renderer/src/outbox.ts) only keeps pending copies associated by session and stable message ID; it does not prove that Runtime executed them. Current reconciliation returns `applied` for `running`/`completed` and `not_applied` for `cancelled`. If a row is missing, product `user_message` facts are used; an existing `outcome_unknown` remains `still_unknown` and must not be blindly resent. “Acknowledge unknown without replay” is a separate explicit operation. It conditionally updates the exact `operation_seq` and removes the item from the projection; it does not determine the execution outcome. The Catalog method name includes “remove,” but it actually marks the row completed, so do not copy an old proposal's description of physical deletion as current behavior.

The Composer releases or retains the copy based on the server reconciliation result; only `not_applied` restores a safe retry prompt. If localStorage writing fails, the current Renderer keeps showing the copy in memory, but this does not prove durable recovery after refresh. Tests should cover missing/existing rows, late reconciliation, duplicate operations, storage failure, and refresh, not just the button. Freezing or displaying the full selection, comments, and citations must be verified against their actual sources and permissions; they cannot be inferred from the queue title.

## Literature Taxonomy and Tags in Conversations

Taxonomy and tag management is discovered on demand through [Bridge registration](../../apps/serve/service/platform/bridge.py). It can be composed independently with literature import and can also organize existing literature. Taxonomies belong to the current session project; tags reuse global definitions. Associations only add or remove selected relationships, and target literature must already exist in the current project; this cannot import across projects. A category with the same name is reused under the same parent, and a tag with the same name is reused. Deletion first returns the impact scope and revision; after user confirmation, the submitted revision is checked and changes made in the meantime cause rejection. Renaming or deleting a tag affects every project that uses it.

Session admission and the actual transaction belong to the [command boundary](../../apps/serve/service/chat/api/commands.py) and [literature store](../../apps/serve/service/literature/persistence/store.py), respectively. Contract tests are in [taxonomy](../../apps/serve/tests/contract_taxonomy.py) and [Bridge](../../apps/serve/tests/contract_taxonomy_bridge.py); tests do not replace real conversation acceptance.

Do not make the interface “neater” by omitting or hiding them or changing the default collapsed state. Decide new interaction changes from actual authorization, the design Owner, component capability, and real acceptance; knowledge cleanup must not cancel unfinished requirements from an old task.

When changing the Owners above, separately validate project menu/card entry points; A→B→A session restoration and continued background tasks; title and user/AI body matches; empty queries; principal/project boundary violations; navigation to the matching message; current-object and explicit references; and late requests/context revision conflicts. Start with focused contracts and Renderer checks, then exercise the real Desktop and corresponding model turns. Documentation checks do not replace product acceptance.

The old plan's requirement for account mode is not the current source of truth for startup or model authorization. Preserve the actual runtime/model authorization prerequisites in the current [development runtime contract](../runbooks/development.md) and Desktop debugging Skill. Service HTTP authentication mode, `healthz`, or successful import does not prove that a business turn passed.
