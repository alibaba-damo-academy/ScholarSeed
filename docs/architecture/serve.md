# Serve Product Composition and Cross-Domain Boundaries

Use this page to identify the Owner before changing backend APIs, session orchestration, or cross-domain dependencies; it is not a complete API catalog or an acceptance report.
First read the [Serve README](../../apps/serve/README.md) and [local rules](../../apps/serve/AGENTS.md).
After identifying the business domain and protocol consumers, go directly to that domain's API and service implementation instead of traversing every architecture page.

## Responsibilities and Composition

Keeping cross-platform Owners and narrow contracts organized by business domain reduces integration and conflict costs caused by frontend/backend group chaining, shared writes to global entry points, and dependencies between private Stores. The backend composition root assembles services, and the frontend composition root mounts public contributions; domains do not construct other domains' services or build their own file storage. A single Owner maintains the design system instead of each domain copying it. The historical “seven-person division of work” was a collaboration plan at the time, not a permanent personnel permission table or a fixed number of domains. When responsibilities or cross-platform protocols change, recheck the actual Owners, consumers, and verification scope instead of copying the old list.

- `apps/serve` independently owns the `scholarseed` distribution, `service` namespace, product configuration, credentials, persistence, HTTP/SSE, and event projection. See [cross-system Owners](ownership.md) for the independent responsibilities of Runtime, Adapter, and Trace; do not restore the old `damoagent` Harness or a compatibility forwarding layer.
- [bootstrap.py:create_app](../../apps/serve/service/bootstrap.py) is the product composition root. It assembles domain services, routes, authentication, and static resources; [chat/runtime](../../apps/serve/service/chat/runtime/) composes the public Runtime contract with product state. Implementations are injected through the composition root; do not use mutable global services shared across application instances.
- [platform](../../apps/serve/service/platform/) contains cross-domain protocols and infrastructure; domain implementations remain with their respective business Owners. Putting business behavior in a shared Port expands consumer coupling; a shared name cannot replace determining ownership.
- Access project files and root paths through [ContentPort](../../apps/serve/service/platform/content.py), and open project business databases through the unified connection Owner. See [persistence boundaries](persistence.md) for paths, user/project ownership, and incremental migrations. Do not assemble project roots yourself or restore the `DAMOAGENT_HOME` path fallback.
- A background task's lifecycle includes actual execution and cleanup. A returned request, disconnected stream, or cancelled coroutine does not prove that a thread, process, or vendor task has ended. For events, cancellation, and terminal states, first check the business-state Owner, then the frontend projection.
- The [skill-list projection](../../apps/serve/service/capabilities/service/management.py) reads local installation metadata through `Activities.observe_thread`; it does not obtain model credentials or occupy the ASGI event loop. A read-only thread may keep running while execution drains; its response barrier remains until the thread ends, but this does not grant execution admission. Plugin file reads, ZIP compression, and integrity checks in [skill reconciliation](../../apps/serve/service/chat/runtime/composition.py) use `Activities.to_thread(RUNTIME)` and retain the actual execution lease. Foreground configuration and background refresh are covered by `finish` for the full reconciliation; cancellation cannot release the serialization lock early or impersonate a drain. Identity, package, and component checks still run in full; do not trade them for response speed by using a cache or skipping checks.

### Startup Source Snapshots and Directory Eligibility

[startup_phase](../../apps/serve/service/platform/startup.py) records `started` and `finished/failed`, process ID, duration, root-directory count, and directory-validation count, quantity, and duration for directory-eligibility acquisition, source snapshots, maintenance initialization, application assembly, and lifecycle recovery. Logs record only counts and error types, not configuration or source data. When aligning Desktop and Serve logs, check the process, port, and startup batch as well; do not compare timestamp prefixes alone.

[Project storage checks](../../apps/serve/service/bootstrap.py) split directory discovery and database-schema reads into synchronized batches. Each batch still validates the complete directory-binding set at entry and exit; do not repeat full-set validation for every project as the project count grows. Without eligibility for the project root or database parent directory, perform discovery only and do not read schemas. Do not create missing projects, cache directory identities, or bypass the storage Owner. macOS uses the existing native POSIX directory checks; Windows uses native handle, identity, and reparse checks. Replacement or read failures must reject the snapshot and clean up owned resources; do not weaken cross-platform security boundaries for startup performance.

## Session Event Replay and Product Search Results

[EventService](../../apps/serve/service/chat/service/events.py) replays by session sequence number from the [persistent event Store](../../apps/serve/service/chat/persistence/events.py). The live queue is used for wakeups; it is not a second source of sequence numbers. Disconnecting clears this subscription; it does not cancel execution. Changes to stream handling must check reconnect cursors, pagination, duplicate projections, concurrent writes, and terminal states. An SSE connection succeeding does not prove recovery is correct, and the old dual SessionHost/WorkSession lifecycle must not be restored.

**current (source)**: The composition root injects an instance-local [ChangeHub](../../apps/serve/service/platform/notifications.py), which publishes ownership-filtered domain invalidation messages through `/api/serve/notifications/events`. A connection registers before sending `ready`; if the backlog exceeds the limit, the client must reread. Idle connections send heartbeats only and do not scan the database. Local transaction triggers are rolled back with the transaction; publication occurs only after the outermost commit succeeds. PDF records are published after their persistence Owner commits. Notifications carry no body, credentials, or annotation content and do not replace persistent state; clients reread the snapshot after reconnecting or switching instances.

**current (source)**: `/api/serve/status` performs bounded reads of summaries, pending interactions, uncertain operations, and queue acknowledgements for owned sessions. It does not open Runtime or change task lifecycles. `summary_seq` is not a body-consumption cursor. Changes to reminder titles and session deletion advance the snapshot revision, but do not rewrite the delivery revision of historical reminders. This channel does not merge with the existing execution stream or monitor direct database or private-file writes by other processes that bypass the business Owner.

[Search Owner](../../apps/serve/service/chat/service/search.py) orchestrates published Invocation results and checks result-body size, markers, schema/provider, and status. Vendor failures become controlled errors; arbitrary JSON, an empty result, or successful registration cannot be treated as completed search. The old Runtime-scoped Search catalog and Lattice settings proposal are not current product interfaces. An external Connector proposal also does not prove existing authorization or an available MCP transport. Check the actual Owner for search, MCP, and domain tools separately; do not restore a generic Harness for a historical proposal.

## Independent Agent Invocation and Direct Inference

`POST /api/agent/invocations` runs an independent Agent; it is not direct model inference such as literature translation. The [route](../../apps/serve/service/invocation/api/routes.py) obtains owner/user from request context, and the [input contract](../../apps/serve/service/invocation/api/schema.py) rejects extra fields. Callers do not submit identity, arbitrary Skill paths, working directories, or raw Codex parameters. A Skill can select a controlled id/profile, and the developer prompt has only a boolean switch; the contract Owner defines the actual fields, defaults, and reasoning levels. Authentication, data ownership, and model authorization remain distinct facts. Disabling local authentication does not imply that a model connection is available.

[InvocationService](../../apps/serve/service/invocation/service/runtime.py) owns preparation, execution, interactions, interruption, and artifact access; the working directory is resolved from the product paths' `ONE_SHOT_DIR`. HTTP must declare that it accepts SSE. Errors before the stream and terminal states within the stream are handled separately; projection is controlled by the allowed fields and named events in [events](../../apps/serve/service/invocation/service/events.py), not by passing through raw vendor messages. File observation, artifact publication, and the final artifact are distinct facts. Interruption and interaction validate the execution owner; an interaction also requires a pending request and an allowed decision. A connection ending triggers execution cleanup, but a disconnected stream, `accepted` acknowledgement, or completed coroutine does not independently prove that the vendor process has exited. Consumers lacking approval-interaction capability must not silently ignore or automatically approve it.

For newly created one-shot invocation workspaces on Windows, explicitly allow the host account to inherit access to subdirectories and files, so Serve can publish files written by the sandbox account. Do not change permissions on caller-supplied trusted workspaces or existing files.

### Invocation Companion Endpoints and Consumer Terminal States

The following paths all use `/api/agent/invocations/{invocation_id}` as their prefix and go through the same InvocationService owner validation. Do not create separate execution or file-access services:

| Method and suffix | Semantics and failure boundary |
| --- | --- |
| `POST /interrupt` | Returning `accepted` means only that the interruption request was accepted; a missing invocation or one not in a running state returns 404. This does not prove the underlying process exited. |
| `POST /interactions/{interaction_id}` | The request body uses the contract's decision/values. Only the corresponding pending interaction can be accepted; otherwise return 404. Do not automatically approve to keep the flow moving. |
| `GET /artifacts/{artifact_id}` | Reads a registered artifact snapshot whose integrity has been verified; arbitrary paths are not accepted. Content mismatch returns 409, a missing file/invalid path returns 404, and other artifact-validation errors return 422. |

Desktop's `src/renderer/src/invocation.ts` consumes POST-SSE and reads artifact text. A stream ending without a terminal state is a protocol failure; only `result.completed` produces a successful result. A pending interaction without a handler or reply fails explicitly; EOF or existing text is not success. Web search also checks the role, expected artifact path, and execution evidence in its own `features/resources/search.ts`; truncating the activity projection must not discard `started`, `terminal`, `final artifact`, or corresponding search evidence needed to determine the result. Successful generic stream consumption does not mean a business result has been verified, and downloading a file does not mean the business artifact is usable.

### Context Snapshots, Claims, and Finalization

An explicit whole-file citation may include an optional `project_id`, stored together with the project-relative `source_id` in the selection, frozen snapshot, and page-safe projection; the source project does not change session ownership. Old citations without a project retain session-project semantics. The existing [resource/read](../../apps/serve/service/resources/api/bridge.py) accepts an optional `project_id`: by default it reads the current project. Cross-project reads must exactly match a readable explicit whole file, path, and frozen version in the current active snapshot, and must recheck the active turn, session binding, and snapshot after reading. Directories, selections, and implicit sources do not grant cross-project whole-file permission; project boundaries for `list` and `stat` do not expand as a result. The composition root injects snapshot queries; Resources does not depend directly on Assistant persistence or create another authorization registry or read command.

Cross-module frontend integration uses [AssistantIngress](../../apps/desktop/src/renderer/src/contracts/assistant.ts) and the [narrow hook](../../apps/desktop/src/renderer/src/features/assistant/ingress.ts): source features contribute candidates or explicit selections; Assistant owns session/CAS/action identity; Viewer owns location and edit transactions. Backend source Providers supply stable identity, version, and controlled reads; do not create an AI-specific Store or read vendor JSONL. Labels and page-instance IDs must not be used for authorization or persistent source identity. This division of responsibilities must not be expanded into “all translation must use the same interface”: Resources AI has an independent domain task; see [the actual selection-action boundary](../features/selections.md#资料解释翻译与润色). Reuse contracts according to the actual Owner; do not restore the old assumptions of a single one-shot or prompt concatenation. For the active document's lightweight current-turn scope, see [frozen identity](../features/conversations.md#聚焦文档是本轮范围不是持久引用或全文). Existing selection-text snapshots also do not switch to rereading the full file when the source version changes.

Assistant resolves session selections into an immutable snapshot. The model card and safe `surface_refs` come from the same source but serve different purposes; model materials must not leak into the user's raw message bubble. `project_policy` and `search_scope` are independent dimensions. Do not restore the old single `project/academic/web` enum or infer backend authorization from UI defaults. Current freeze saves a snapshot and verifies `model_card_hash` on rerender; on failure it releases the exact turn claim. Retry also validates snapshot identity, question hash, and the original claim; it does not reclaim citations added later. The `consume_claim` transaction in [AssistantStore](../../apps/serve/service/assistant/persistence/store.py) deletes only the claim for the corresponding session/client turn and increments the selection revision only when it actually deletes an item.

Persisting a snapshot is not the same as consuming materials. Current finalize consumes on ACCEPTED/DISCARDED, releases the claim while retaining citations on REJECTED, and keeps the selection on UNKNOWN; do not copy the old description “clear immediately after admission succeeds.” TurnService records a context-finalization failure without rewriting the original turn result, so a successful original turn does not prove finalization succeeded. Verify admission failures, unknown acknowledgements, explicit discards, concurrently added citations, invalidation of old-snapshot claims, and finalization errors separately; checking only that a chip disappeared or an API returned is insufficient. This describes current mechanisms and boundaries, not proof that all product requirements in old proposals or real-business acceptance are complete.

When Desktop creates a session while uploading an attachment for the first time, [Composer](../../apps/desktop/src/renderer/src/components/business/Composer.tsx) first calls prepareAiContext to save the pending context; on failure it reports the error and stops activation. Otherwise, activation may load session context over the original draft. [Store](../../apps/desktop/src/renderer/src/store.tsx) uses the read revision to update required refs/policy; do not create an attachment-specific context Store that bypasses this point. Session retention and next-turn consumption have different semantics. Verify current-document automatic citations, manually explicit citations, and sent citations separately; removing a current citation does not erase history or clear context the model has already read.

The frontend submits stable identities and structured context, not arbitrary absolute paths in place of domain identity. Saving an answer to materials goes through [ResourceWriter](../../apps/serve/service/resources/service/writer.py) and the Content boundary. Agent file delivery and long-term source-file versions belong to Resources; do not create another source of truth for writes or versions. PDF viewing/reading records and source-file versions must have distinct Owners; restoring a source file does not automatically authorize overwriting a reading record. See [selection knowledge](../features/selections.md) for the difference between selection snapshots and source actions.

Content file events already have a subscription service, HTTP stream, and Desktop project-event consumer; do not reuse the historical conclusion that there are “zero consumers.” When changing cursors, project scope, or event identity, check the [Content API](../../apps/serve/service/content/api/routes.py) and [Desktop consumer](../../apps/desktop/src/renderer/src/features/project/events.ts). A UI refresh does not mean the authoritative disk write has completed. A description of a fixed business flow only states the Owner boundary; do not use old enums to restrict newly registered capabilities or bypass controlled protocols.

### Workbench Content Classification and Preview Eligibility

The [format model](../../apps/serve/service/workbench/domain/model.py) selects known formats by registered suffix. For an unknown format, limited bytes are classified as text and shown in the basic code viewer only if strict UTF-8 decoding succeeds and there is no NUL. Invalid encoding is not guessed as text using replacement characters. Binary bytes with a known text suffix are also rejected for text preview; `.txt` alone does not permit editing. Basic preview, automatic formatting, native revision, and version eligibility are assessed separately. An editable file with no extension does not thereby gain formatting or version capabilities.

The [open API](../../apps/serve/service/workbench/api/routes.py) first uses a Content snapshot to decide the path, existence, and revision, then handles size, viewer, and capability projection. Files exceeding the preview limit return `oversized` and `file_too_large`; they are not mislabeled as binary. Some registered byte-independent viewers do not need to read the entire file when it exceeds their read threshold; do not infer from unknown-text classification that every format is fully decoded. Final `can_version` is also overridden by the Resources admission capability; model defaults are not authoritative persistence state. Desktop consumes the returned protocol; do not add a read path that bypasses Content or make another extension-based decision.

Unknown-content cases in the [file-workbench contract](../../apps/serve/tests/contract_file_workbench.py) cover editing and saving a Dockerfile, NUL, invalid encoding, disguised text, and oversized placeholders. Actual changes also require opening and editing in Desktop, an independent readback, and a screenshot of the placeholder. Historical acceptance commands and success records are not evidence of passing this time. When content classification, read limits, or admission eligibility changes, the Workbench/Content/Resources Owners must each check consumers and tests; do not expand path or version authorization by adding preview capability.

## Actual Admission of Managed Execution Credentials

Platform Skill credentials belong to [SkillCredentialService](../../apps/serve/service/identity/service/skill_credentials.py). Identity comes from the existing verification service and current account credentials; it is not inferred from the Renderer login flag, cache presence, or a machine-level Session principal. Product-session ownership and real account identity are separate axes. Ordinary model-connection keys remain with ModelCredentialPort and are not part of the platform Skill-variable policy.

Current Skill credentials are requested from the account service using a fixed global slot. A user access token and a Skill API key serve different purposes and are not interchangeable; the service constants define the request endpoint and slot, which are not derived from the project path. Local caching and request shape do not prove that enterprise issuance/revocation, visibility of all active keys, or multi-device behavior has been accepted. Nor should the historical rule “returned only at creation” be applied to the retrieval contract for managed slots.

At actual admission in `prepare_turn`, [SessionService](../../apps/serve/service/chat/service/sessions.py) reads `admission_environment` and compares the current authorization projection again after waiting for resources; do not take the snapshot only once when the message is queued. An active turn is not proactively interrupted to change credentials; queued messages are re-admitted before execution. Credential-service revocation increments a revision. After asynchronous issuance completes, check the revision and current identity; expired issuance must not be written back to the cache. If the authorization projection changes or alignment fails, reject new execution rather than falling back to old authorization to remain “available.”

Current [Runtime composition](../../apps/serve/service/chat/runtime/composition.py) first lets idle attachments exit quietly, then updates the environment for subsequent admission after success; do not reuse the old description of “immediately restoring the original vendor binding.” Verify session, binding, and history retention separately from successful real resumption; a single configuration update does not prove recovery passed.

The [product secrets Owner](../../apps/serve/service/chat/runtime/secrets.py) declares the set of platform/Bridge variables to remove and passes values through secret refs; the public Runtime contract handles only the generic set and does not own product-variable constants. The [Codex process](../../packages/adapters/codex/scholarseed_codex/process.py) first removes named keys from the inherited environment, then applies the explicit environment. [Argument parsing](../../packages/adapters/codex/scholarseed_codex/executable.py) does not reread removed parent variables, and the [process pool](../../packages/adapters/codex/scholarseed_codex/pool.py) identity includes the removal set. An empty string is not removal, and a secret-intent revision is not proof of account authorization. This boundary does not modify system environment, user model keys, or other hosts; never write secret values to ordinary snapshots, logs, or knowledge records.

For changes, selectively check the [credential contract](../../apps/serve/tests/contract_skill_credentials.py), [identity contract](../../apps/serve/tests/contract_auth.py), [session contract](../../apps/serve/tests/contract_codex_service.py), and [Adapter contract](../../tests/contract_codex_adapter.py). Real product validation must additionally cover visitor/login/logout, queuing before logout but executing after logout, revocation while waiting, issuance races, error recovery, and resume after restart, while observing non-secret presence and actual tool behavior. Do not output real variable values or copy user credentials; auth-off or a health endpoint does not prove model authorization. Old acceptance reports, versions, and screenshots are historical evidence only; this knowledge-governance work does not run those product flows.

## Logical Sessions, Execution Residency, and Capacity Reclamation

[SessionActivation](../../apps/serve/service/chat/runtime/activation.py) coordinates on-demand activation and safe candidates for product sessions; the existence of a logical session/history does not mean an execution process must stay resident. Capacity pressure must not delete sessions, automatically interrupt tasks, or broaden shared compatibility keys to free capacity. Actual vendor processes belong to Adapter, and the [neutral resource contract](../../packages/runtime/scholarseed_runtime/contract/resource.py) carries no credentials or process compatibility keys. Historical fixed execution/control counts are not the current configuration source of truth. Check Adapter policy and host-injected admission separately; default numbers or resource readiness are not evidence of safe release.

[LiveSession](../../apps/serve/service/chat/runtime/live.py), while holding the lifecycle lock, rejects running, interrupting/terminating, steer, unknown-result, unfinalized resource-task, and pending-HIL states; a failed check is not proof of idleness. [Gateway suspend](../../packages/runtime/scholarseed_runtime/gateway/driver.py) retains a single consumer until ticket-watermark projection completes, then commits after executing a checkpoint. Exceptions are handled by querying PREPARED/COMMITTING/RELEASED; cancellation is not treated as undoing a committed release. The current Live checkpoint calls a Trace checkpoint; this callback alone cannot prove that all business artifacts have been persisted. If there is no driver, successful product-local finalization still does not prove that all physical Provider resources were released.

The [Codex pool](../../packages/adapters/codex/scholarseed_codex/pool.py) closes physical resource leases, removes slots, and wakes waiters only after the host stop call returns; STOPPING still holds resources. Native unsubscribe, UI closure, or an isolated systemError is not sufficient proof that all activity has ended. For a native failure in a quiescent state, check the remaining activity and generation. The pool itself does not resend a submission with an unknown result or rewrite the original thread or user history. After exact native checks, confirmation, and ledger CAS, the [recovery Owner](../../apps/serve/service/chat/service/recovery.py) orchestrates a successor under a persistent one-time budget: restore the result if complete, continue remaining work if partially complete, or retry the original input and frozen context with a new submission ID if still unknown. An unknown-result retry accepts duplicate-side-effect risk; it does not prove native idempotency or that the request was never submitted. Confirmation, CAS, admission, or release failures retain the fence, and historical unknowns are not replayed in bulk.
When native-thread recovery accurately confirms that history is missing, the recovery Owner can obtain typed credentials through Runtime's separate two-phase `RuntimeThreadReplacement` port, proving that the old failed generation exited and the current thread is missing and fenced. This is not `EmptyThreadReplacementProof` and does not prove that the original request was not executed. Gateway waits for the observed watermark projection; Adapter verifies the generation, native activity, callbacks, and attachment identity before fencing the old input. The product retains the original UNKNOWN event and old checkpoint; only the exact old turn may complete unknown settlement, and it cannot synthesize completed or interrupted. Other threads on the shared Host are not closed or replaced as a result.

Serve distinguishes empty-thread replacement from `history_rebuild` in the same persistent replacement model. It saves a fence before creation and performs CAS after saving the candidate using the complete binding, configuration, queued operation, and attachment generation. A lost creation ACK, cancellation, or uncertain initialization remains UNKNOWN; startup does not create again automatically. A subsequent independent user task may obtain a new one-time budget after the previous replacement is BOUND. The previous replacement record remains, and the same task cannot be reopened.
The new thread receives product-portable messages through the public initialization contract. The successor uses a new command ID and checkpoint epoch, with sourced observations of tool completion, artifacts, and plans; these observations are not new instructions and do not prove external state is unchanged. Check existing results first, then continue unfinished work; do not resend the original user message as new input. This is bounded automatic task continuation, not lossless native-history recovery, and it does not guarantee exactly-once execution of unknown external side effects.
The current entry point requires a live Serve instance to hold the checkpoint for an unfinished task in this turn. Completed idle sessions, the next unsubmitted request, and missing history at cold start do not automatically enter this path; an old COMPLETED state is not changed to UNKNOWN. The successor still goes through ordinary `prepare_turn` and does not skip per-turn attachment refresh on Windows. Before preparation, the recovery Owner freezes the original claim, same successor queue, configuration, and execution identity. After preparation it checks the same Thread, a complete quiescence snapshot, and a valid resource lease, then persists a one-time `prepared` re-admission. The original claim and UNKNOWN are not rewritten. A new attachment accepts only the exact identity produced by this preparation; later drift cannot be re-signed. An issued native-admission fence can be consumed only by this successor's automatic checkpoint; ordinary new turns, cancellation, configuration changes, or maintenance revoke authorization.
Releasing a physical model bridge does not mean its connection authorization can be reused. Cross-attachment continuation with existing model authority also requires the model Owner to verify a same-source valid registration and hand off new authority; the old registration remains invalid. Revocation during the release gap must not be missed. If no old model request was observed, do not fabricate authority; retain full preparation and quiescence fences.
The renewal fingerprint is captured only before the first wait for the first model request of the current unfenced checkpoint; later requests do not reread configuration for that checkpoint. Recovery still rechecks the complete intent digest, credentials, and revocation generation, but does not establish a new request baseline during recovery. The fingerprint retains only a digest of the normalized complete payload. Sampling failures record only a safe exception type and session identity, never credentials, payload, or raw exceptions.
