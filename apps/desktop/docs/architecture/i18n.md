# Desktop Internationalization Architecture

## Scope / Non-goals

Desktop uses `i18next + react-i18next` to internationalize application-owned copy, initially supporting Simplified Chinese and English. Coverage includes application-owned interfaces in the Electron renderer and Electron main process, browser renderers, formatting, accessibility copy, and language coordination with embedded editors.

Internationalization applies only to application UI text. User messages, AI-generated content, paper text, file paths, code, user-provided names, protocol values, logs, and raw upstream errors remain unchanged. It does not change the language of AI responses, the target language of translation features, currency, or the user's time zone. Do not introduce a translation cloud service, runtime machine translation, remote language packs, or a second store for language preferences; UI internationalization does not belong in Runtime, Adapter, or Trace.

Application-controlled native menus, permission explanations, launch screens, and notifications are in scope. Operating-system buttons, external webpages, and interfaces inside third-party applications are not application resources; handle them through each platform's or component's own language mechanism.

## Source of truth

Language registration, resources, instances, and consumption boundaries are as follows:

| Location | Responsibility |
| --- | --- |
| `src/preferences.ts`, `src/locale.ts` | Language mode, runtime projection to `zh/en`, and system-language detection |
| `src/localization/catalog.ts` | Supported languages, endonyms, BCP-47 tags, number/date locales, and Office locales |
| `src/localization/locales/{zh,en}/*.json` | Authoritative Chinese and English messages stored by namespace |
| `src/localization/engine.ts` | Creation of consistently configured i18next instances, fallback, and diagnostics |
| `src/localization/resources.ts`, `types.d.ts` | Static imports and type contracts generated from the resource inventory |
| `src/renderer/src/app/localization.tsx` | Renderer instance, root Provider, language switching, and HTML `lang` |
| `src/main/localization.ts` | Main-process instance and native UI copy |
| `src/renderer/src/components/ui/` | Consumes only `ui` messages or explicit copy props |
| `src/preferences.ts`, `src/persistence.ts`, preload | The sole persistence and confirmation path for language preferences |

JSON is the sole source of copy. `resources.ts` and `types.d.ts` are generated files; do not maintain a second key inventory by hand. Language resources are statically imported and packaged with the app for offline use; they are never loaded from the network at runtime. A namespace is a stable domain boundary. Create its resource file when product copy first appears in that domain; do not pre-create empty dictionaries. The foundational namespaces loaded by the current implementation and later domain namespaces belong to the same resource model; temporary non-loading does not change ownership.

## Namespace and ownership

Namespaces are divided by business domain and code owner, not by individual page or component. Translation files are physically grouped under `src/localization/locales/{zh,en}/`; the corresponding domain owner is responsible for message semantics.

| Namespace | Responsibility |
| --- | --- |
| `foundation` | Startup failures, internationalization initialization failures, and global foundational faults |
| `ui` | Shared copy and accessibility text for design-system primitives, such as close, copy, pagination, and resizing |
| `account` | Sign-in, model connections, notifications, permissions, diagnostics, and developer settings |
| `shell` | Global navigation, project/session menus, home, panels, launch interface, and app notifications |
| `conversation` | Session recovery, send/retry, model selection, run status, message chrome, and tool actions |
| `subscription` | Subscription model connections, sign-in/disconnect, model selection, and related request/IPC failures |
| `project` | Project creation, editing, selection, and removal |
| `assistant` | Assistant panel, context, citations, and artifact display |
| `resources` | Resource library, import, resource tree, move, copy, and resource search |
| `literature` | Literature search, import, batch operations, details, excerpts, and citations |
| `workbench` | Workbench chrome, tabs, Dock, save status, file operations, and Markdown/Monaco/Office application chrome |
| `pdf` | PDF navigation, search, annotations, evidence, and reading results |
| `tasks` | Background tasks, plan status, progress, and waiting notices |
| `skills` | Skill listing, installation, deletion, enable/disable, and categories |
| `native` | Native interactions owned by main, such as file/directory selection and saving; startup failures belong to `foundation` |
| `examples` | Component examples and design-system demo data |

Keep `foundation` and `ui` small and stable; do not put business errors or domain operations there. The existing `components` namespace is only a compatibility container during migration and retains existing cross-domain display messages; new business code must not add keys to it. After migration, narrow and remove it by business subtree, leaving no forwarding keys or duplicate resources. `examples` is only for component examples and test demos; production code must not depend on it. User content, filenames, and AI content in examples are not product copy to translate.

Determine cross-domain reuse by semantic owner: shared interaction actions belong in `ui`; business actions and states belong to the domain that owns that state, and other domains consume that domain's key directly. Do not copy a key into `components` or `ui` merely because multiple pages use it.

React business code uses `useTranslation(namespace)` or `Trans`. Pure TypeScript modules explicitly receive a translator, a function bound to a fixed namespace, or a formatter. Main uses only its main-process instance; the renderer does not import main, and main does not import the renderer resource aggregator. Components do not create i18next instances, read business stores, or keep their own language cache.

## Message design

Keys express stable user-facing semantics; messages use complete sentences and named parameters:

```tsx
const { t } = useTranslation('resources')
return <Alert description={t('import.failed', { name })} />
```

```json
{
  "import": {
    "failed": "无法导入 {{name}}。"
  }
}
```

English resources preserve the same logical message and parameters while following English word order. Do not split sentences into Chinese word fragments, maintain `lang === 'en'` branches in pages, or concatenate runtime keys arbitrarily.

Handle plurals as logical messages through i18next. Each language provides the plural branches it needs. Validate logical messages, parameters, and branch coverage; Chinese and English JSON leaf keys do not need to match verbatim.

For rich text, use the controlled `components` and `values` of `Trans`, allowing only React components supplied by code. Arbitrary translated HTML and `dangerouslySetInnerHTML` are prohibited.

`title`, `label`, `description`, `placeholder`, `aria-label`, tooltips, toasts, errors, empty states, and status notices have the same internationalization requirements as ordinary visible text. Design-system components receive copy through props; the business layer supplies domain messages.

## Errors, status and formatting

State that can be re-rendered stores stable error codes or message IDs and parameters, and translates them at display time; never write the current language's translation into business state, sessions, or the database. Map backend protocol error codes explicitly and in a typed way to UI keys. For unknown errors, preserve diagnostic details and show the application's own localized explanation. Unknown error codes must not be concatenated directly into resource keys; show a generic localized explanation and retain the raw code and details in the diagnostic area.

When app-generated labels and user-authored text share a business field, keep the original label as the business truth and carry a constrained provenance value separately; the display layer translates only portions explicitly marked with provenance. Display historical data without provenance as-is; do not guess that a Chinese string is an app label. Switching languages does not modify business labels, model context, or selection revisions. See the provenance constraints below; do not rely on paths from old proposals.

Chinese and English default templates for AI prompts are editable business-content seeds owned by `src/prompts.ts`, not display chrome translated with the interface.
When a prompt is first missing, populate it using the product's already-determined initial UI language; persisted `selectionPrompts` always has a single copy.
Switching the UI language does not change valid existing values or editing drafts. “Restore defaults” replaces only the corresponding draft using the currently confirmed language; it takes effect only after the user saves through the existing preference write path.
Actual AI instructions continue to consume the same saved body. There is no automatic migration, content-based default detection, or dual write of Chinese and English user settings.

Format dates, relative times, numbers, and amounts with `createFormatters(language)` and an explicit locale. Changing language changes only display formatting; it does not change currency, precision, time zone, sorting, search tokenization, or code-language detection.

## Label provenance and frozen business identity

Provenance indicates which parts were generated by the app; it is neither another translation service nor an arbitrary template parameter.
This tradeoff must be preserved: a Chinese label may be default copy or a real user-provided name. Guessing from the text would rewrite user data and let language switching affect model input, idempotency digests, or sent history.

- Session `title_fallback` and citation `label_fallback` are separate contracts; map them explicitly from provenance observed under the same authorization. Do not treat a default label synthesized for a catalog listing as the real title of the historical source. Select a real non-empty title together with its provenance marker; renaming or accepting a generated title clears the old marker at the same time. Do not attach an old marker to a new title.
  An empty source title may inherit a frozen citation under existing rules; do not guess or backfill fields missing from historical data.
- The constrained citation provenance values apply only to sessions; `selection_source_label` applies only to selections/literature with an anchor. An explicitly empty string and an absent field are different facts. Do not strip the “text selection” suffix from a real title or reconstruct a missing literature title from the path basename.
- On successful citation resolution, freeze both the label and provenance fields. A failed issue inherits existing frozen provenance; do not read unauthorized content just for display. Historical display uses frozen fields. A preview's observation of the current source and historical freezing serve different purposes; opening a preview must not activate a source session or modify history.
- A model provider's provenance supplies preset identity only in a genuine preset branch. Do not automatically translate a user's `preview_name`, even if it matches an app label. Use the existing model display function; preserve unknown sources verbatim, do not parse delimiters, and do not depend on whether the settings page has loaded its profile cache. Menu grouping/layout follows the current Owner; do not restore the old combined-label format from historical proposals.
- Skill category `category_source` marks only default source labels generated by the app. The two bundled build entry points explicitly produce the `builtin` marker. Serve adds a default label based on the actual source when a category is missing, and ignores forged markers in user metadata. Desktop translates only marked default labels and preserves the business value of `category`; historical categories without markers, custom categories, and unknown markers remain unchanged. Do not guess provenance from “system built-in/user-installed.”
- Optional provenance columns are stored additively by the existing SQLite Owner; an old NULL means provenance evidence is absent, not that a label should be backfilled. Admission digests exclude `label_fallback` and `selection_source_label` while retaining other business fields and their encoding; this does not make arbitrary new fields excludable. Model cards and model context continue to use business text. Switching languages must not PATCH a selection, increment its revision, or change its claim/authorization.

The actual contracts and implementations are described in [Serve context](../../../../apps/serve/service/platform/context.py),
[citation resolution and digest](../../../../apps/serve/service/assistant/service/context.py),
[session provenance resolution](../../../../apps/serve/service/chat/service/context.py),
[Desktop citation display](../../src/renderer/src/features/assistant/text.ts), and
[model display](../../src/renderer/src/components/business/profile.ts). After changes, cover old and new data,
user labels matching app labels, provenance changes on rename, empty titles, and failed/queued/historical/preview round trips. Verify that when only display
semantics change, digests and model bytes remain unchanged. Entry points include
[provenance tests](../../src/renderer/src/features/assistant/provenance.test.ts) and the relevant Serve
context/selection contracts. Real acceptance is still required for language switching, restart, model menus, and history flows.
This document update carries forward existing knowledge; these behaviors were not rerun and screenshots from historical proposals were not rechecked, so this is not reported as end-to-end acceptance.

## Runtime and process boundaries

Skill reference names are presentation metadata, not invocation identity. Message streams
share a name-only catalog snapshot scoped to an account identity generation. Remounting
or refreshing the same identity retains resolved names. Language changes project existing
multilingual metadata immediately; stale identity, locale, or catalog responses are rejected.
An unresolved catalog uses the localized skill-type label before a confirmed miss or failure
falls back to the original reference title. User titles, canonical name/path/version, history,
and model input remain unchanged. Account notifications live for the renderer document
lifetime, and remounted consumers synchronously read its current identity snapshot.

At startup, main reads the confirmed preference and initializes its own instance first. Main loads only the `foundation` and `native` namespaces it needs; it does not load the renderer's business resource aggregator. The renderer initializes resources with the same confirmed language, sets `document.documentElement.lang`, and then uses the root Provider for pages, Portals, Dialogs, and Toasters. Both processes may statically import the same authoritative JSON, but always create separate instances. A browser renderer obtains preferences through the existing bridge and does not access Electron.

Language changes are committed serially through the existing preference write queue. The UI treats the target language as committed only after persistence, the main-process projection, and renderer application all succeed. On save or application failure, feedback must use the committed language; retries and reconciliation against the authoritative preference must be supported. Multiple windows must not write language preferences independently.

New preferences default to following the system; existing `language: zh/en` values remain fixed. Follow-system mode stores only
`languageMode: system`, never the detected result. Use Chinese when the first available system language has primary subtag `zh`,
and English otherwise. Only when no system language is available, use the time zone as the basis; default to Chinese as a last resort. Both macOS and Windows obtain
the system language list from Electron; the Web version uses the browser language list. Follow-system mode reads the language at startup and when the main window regains focus; it does not poll, reload the page, or rewrite preferences. If a Monaco edit is unsaved, skip automatic switching and check again on the next focus after it is handled. Manual switching continues through the existing confirmation and save flow.
Construct explicit language snapshots for previews separately from actual new configuration; fixed-language snapshots do not carry system mode.
If focus-time refresh fails, offer retry through the existing preference error notice. On application failure, attempt to restore the old projection; a refresh that is not restored blocks exit confirmation. Retries remain protected by dirty-edit checks and do not write to disk. Successful explicit preference commits may also restore synchronization.

Already delivered notifications are not rewritten retroactively; new notifications use the confirmed language. An open system dialog is not forcibly closed on a language change; the new language is used the next time it opens.

## Editors and native surfaces

[Monaco frame host](../../src/renderer/src/features/workbench/monaco/host.tsx) uses
a same-origin build entry and the current preferred language. A ready message must match the iframe Window, origin, message
type, and the random token for the current load; switching/unmounting clears listeners and frame references, so an old
instance cannot be accepted based on origin alone. The [frame entry point](../../src/renderer/src/features/workbench/monaco/frame.ts) installs NLS
before loading the runtime. A current query other than `zh` is normalized to `en`; this is not a
validator that rejects every invalid query. iframe realm isolation supports the NLS lifecycle; it is not a cross-origin
security sandbox, and iframe DOM must not be attached to the parent window to bypass which Window owns focus/selection.

Office retains its own gettext/WASM resources and language mechanism; the app passes only `zh-CN` or `en-US` registered in `catalog.ts`. Monaco NLS copy is fixed when modules are evaluated, so each mounted code viewer owns an independent Monaco module graph in a same-origin iframe. After a language commit succeeds, rebuild only those frames and restore files, cursor, selection, and scroll position from the existing document session and view state. Do not reload the app renderer, current page, project, or tabs. If no Monaco document is unsaved, commit the preference and rebuild the frames directly. If a document is unsaved, obtain explicit confirmation first and save only Monaco-backed documents. Do not commit the language if saving fails, an external conflict occurs, or any Monaco document remains dirty. Keep ordinary Chromium reload shortcuts disabled; language switching must not have access to renderer reload IPC. Editor instances must record their actual locale and must not reuse a runtime context from the old language.

The `native` namespace and main-process instance own native menus, launch screens, permission explanations, and native notifications. If a third-party editor or operating system lacks the corresponding resources, document the support boundary clearly; do not present fallback or external interfaces as fully translated.

## Validation constraints

Resource checks must validate language registration, namespaces, keys, interpolation parameters, and plural branches; generated files must match the JSON inventory. Source checks constrain new visible hard-coded strings and legacy dictionary consumers, and cover JSX text, display attributes, tooltips, feedback calls, and explicit display fields.

`fallbackLng` is only for startup failures and observable degradation; it does not count as coverage for normal business copy. Release checks require zero missing translations and zero fallback in the target language for every in-scope namespace. Missing translations must be diagnosed and block release.

Release scope consists of current production routes and pages, main-process native menus/launch screens/permissions/notifications, and all business components loaded from production entry points. `examples`, test fixtures, protocol details, user content, and external pages are not product-copy scope. Static gates prove only resource and call contracts, not coverage in the real UI. The release scope must also be verified through real Desktop or browser product flows covering language switching, Portals, toasts, errors, settings, the workbench, and editor boundaries.

## Examples and anti-patterns

```tsx
// Good: a domain component consumes its semantic namespace directly.
const { t } = useTranslation('resources')
return <Alert description={t('import.failed', { name })} />
```

```tsx
// Bad: a page maintains a language branch or stores a translated string.
return <span>{lang === 'en' ? 'Import failed' : '导入失败'}</span>
setError(t('resources.import.failed'))
```

## Enforced by

`pnpm ops ci test integration --scope tooling --suite i18n` and `pnpm ops ci check i18n` validate resources, generated output, call parameters, plurals, and visible-source debt; `pnpm ops ci check types desktop` validates typed keys and parameters. `pnpm ops ci check docs desktop` validates this document's structure and links. These gates do not replace real product flows; real bilingual acceptance must be completed through the owning product entry point.

## Update triggers

Update this document only when changing language registration, resource loading, instance boundaries, preference confirmation semantics, namespace ownership, editor language coordination, or validation contracts. New business copy needs changes only to the Chinese and English resources and consuming code in the relevant namespace; do not record implementation progress, execution plans, or design comparisons here.

## Stop condition

The internationalization foundation satisfies this design when the architecture boundaries, authoritative resources, process synchronization, error/formatting rules, and validation constraints described here are implemented. Business pages migrate domain by domain under their respective owners. Do not describe unmigrated pages, external interfaces, or editor capabilities as complete bilingual support.
