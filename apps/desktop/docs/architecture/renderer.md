# Renderer Architecture

## Scope / Non-goals

Covers the React renderer composition root, feature contributions, shell, and shared contracts. It does not define Serve business logic or Electron packaging, and does not enumerate dynamic feature counts.

## Source of truth

- `src/renderer/src/contracts/features.ts`: `FeatureModule` and contribution protocol.
- `src/renderer/src/app/composition.tsx`: the sole feature composition root.
- Each `features/<domain>/feature.tsx`: domain contribution declarations.

## Current / Required / Gap / Advisory

- **current (input preparation)**: When task cards or reading content populate a draft, `revealConversation` restores conversation visibility while preserving the workspace's open/closed state, side, and width. Explicitly opening a document or the workspace still uses its respective explicit action. / When task cards or reading actions prepare a draft, `revealConversation` restores the conversation while preserving workspace visibility, side and width. Opening a document or the workspace remains an explicit action.

- **current (input while running)**: When the current task can be stopped, the Composer shared by the main conversation and assistant shows only the Stop button; it does not show the send arrow even if the draft contains text or a queue item is being edited. Enter retains its existing submit/queue and queue-edit save behavior, while Shift+Enter still inserts a newline; the existing submission barrier remains in force while stopping. The Send button returns after the task ends and no accepted message is still awaiting Runtime. This is a user-confirmed button-visibility requirement; it does not cancel the persistent queue or change execution admission.

- **current (conversation scrolling)**: When a confirmation is pending, shared `ConversationControls` limits the combined height of the confirmation card and input area to three quarters of the parent conversation container, preserving room to view message history. Short content still uses its natural height; with no pending confirmation, the existing full-height maximum remains. The question list inside `PendingHilDock` continues to scroll independently, and the outer container does not clip popovers opened upward from the input. The main conversation and assistant panel share this constraint; the ratio is a layout derivation for access to long content, not a claim that it comes from a fixed MasterGo artboard.
- **current (skill installation)**: A generated skill's pending installation card is docked above the input by shared `ConversationControls`; it does not scroll with the message stream or enter the blocking confirmation queue. After the host confirms installation or skipping, the card returns to its original message position, retaining its installation status and existing actions.
- **current**: A new conversation reuses the last explicitly selected model and restores reasoning effort from `reasoningPreferences` in the current Electron profile using the full model key. If the target has no valid preference, use its declared default; do not inherit another model's level. An old conversation restores its own saved selection, and browsing history does not change new-conversation preferences. Model and effort changes share a selection barrier. Sending freezes the selection generation and effective effort; a change made while waiting invalidates only the old send and preserves the draft, without replaying failed or unknown messages. Persistence reuses `PreferenceWriter`'s acknowledgement and existing failure retry; it is not a cross-store transaction with saving the Serve default model.
- **current**: The draft is not cleared during send preparation, conversation creation, attachment registration, or input validation, so failures in those stages do not write the original text or references back a second time. After it is actually cleared, restore this send's text and merge new input only for an explicitly unsubmitted failure. Determine this from the clearing stage of the current send, not by deduplicating content; preserve legitimate duplicate input. Do not restore accepted or outcome-unknown messages as pending drafts.

- **current (context refresh)**: Initial assistant loading and a background refresh of the same conversation use `loading` and `refreshing`, respectively. Both retain send-readiness validation, but neither inserts loading copy into the input. A same-conversation refresh preserves references and drafts; an older response cannot overwrite newer references, and readiness is restored when the read finishes. A load failure retains an explicit error, and save-in-progress feedback does not replace existing references. The message area retains task-execution feedback; the input does not duplicate foreground-running status, and interjection messages no longer receive an added text marker. The interjection protocol and history remain unchanged.
- **required (directory refresh)**: Metadata entry points share one in-flight request and a coalesced dirty follow-up. A background refresh must not downgrade a ready workspace to its startup loading or error screen; on refresh failure, retain content and an explicit recovery prompt. Evaluate queued status updates against the current state at execution time; do not let a ref that has not yet been updated by React commit overwrite `ready` in the same batch. Initial loading and error recovery must still preserve their actual loading, failure, and retry states.
- **current**: The shell reads the composed registry; viewers, module panels, document panels, commands, toolbars, and assistant sources are composed through contributions. A document panel receives only stable document identity; the owning feature matches and renders it, and Workbench owns the sole host for contributed side panels. Viewer contributions are split into on-demand chunks by kind. The composition root applies loading and error boundaries once during assembly; shell consumption sites do not each wrap themselves in Suspense. A load or render failure in one viewer shows an error for that document only and preserves other documents; changing document identity recreates the boundary.
- **current**: The stable navigation pointer defined in `src/navigation.ts` saves the last page to the existing `RendererPreferences`; page, settings subpage, project, conversation, and active-document changes reuse `PreferenceWriter` for persistence. `src/renderer/src/navigation.ts` validates directory identity. After Store and the project and conversation directories are ready, it restores navigation and then permits saving the current navigation; writing preferences back does not navigate again. Workspace documents are genuinely reloaded; bytes, unsaved edits, drafts, and transient popovers are not saved. A deleted project, conversation, or document returns to the home page and clears settings and assistant context from the recovery location; first run still opens home. The document's project and the docked assistant conversation's project are saved separately and cannot substitute for each other.
- **current (recovery fallback)**: Store binds `returnHome` to the recovery context in `contracts/navigation.ts`; loading/error screens and render-error screens share the same action to return home. The action synchronously invalidates the recovery generation, preserves the actual directory-loading state, and saves home through the original preference writer. Async results, failure handlers, and queued submissions for recovered conversations, documents, and tabs all check the generation and effect lifecycle, so they cannot navigate again or overwrite the home preference after returning. Network and permission errors are not treated as deleted targets; home still retains directory-failure details and retry. If Store's outer layer crashes, the composition root recreates the boundary and explicitly replaces this run's startup recovery location with home; it does not modify user assets or add another persistence store.
- **current**: Project workspace layouts are isolated by server project ID through `src/layout.ts`. `RendererPreferences.projectLayouts` and `PreferenceWriter` persist panel visibility, width, left/right swap, and full-screen state; a project without a saved layout shows only the conversation. Both project switching and startup recovery read that project's layout during Store state transitions and do not reuse the previous project's split. Width is saved when dragging ends. A change to the active tab caused by switching projects does not automatically reopen a closed workspace; a user explicitly opening a document still opens the workspace. Layout is a local UX preference and is not written to project business assets or directories.
- **current (width ownership)**: `ProjectLayout.conversationWidth` stores the conversation area's width in pixels, defaulting to 360; tabs consume the remaining space. Collapsing navigation, widening the window, and swapping sides do not assign the added space to the conversation area. After a manual resize, width is saved per project, while both sides continue to honor their minimum widths in constrained space. The legacy `width` means tab width and must not be interpreted directly as conversation width; if the new field is absent, use the new default, while other layout fields retain their own semantics. See the [public design contract](../design/foundations.md) for real Web verification; it does not constitute native Desktop or Windows acceptance.
- **current (explicit project draft)**: When `startDraft` receives a project ID, it opens that project's workspace instead of retaining a global page such as the skill center; skill references, description, and one-shot send request are carried in the same state update. Only the assistant Composer in the project workspace consumes the send request, and it waits for the existing send gate to become ready; the request is not silently discarded while the skill catalog, model, or runtime is not ready. Submission still goes through the original `submit` single-flight, permission, and failure handling; it does not call the backend directly to bypass Composer. See the [public design contract](../design/foundations.md) for real-model acceptance and build limitations.
- **required**: New business capabilities MUST be owned by their feature; cross-feature assembly MUST use stable contracts/registries. Do not add branches hard-coded by domain name, extension, or state to `App.tsx` or the shell. Heavy dependencies needed only after opening a document type MUST NOT be statically included in the initial bundle. The shell MUST NOT statically import a viewer's implementation module just to use a helper function: that edge pulls the viewer's entire dependency tree back into the initial bundle. Reclamation of resources cached across conversations is instead registered by the viewer module itself.
- **gap**: Some legacy UI and global state have not fully migrated to feature contributions; their existence does not mean new code may copy that pattern.
- **current (embedded preview source)**: In-page previews are associated with their host tab through `DocumentTab.hostTabId`; different hosts for the same document retain independent preview projections while sharing a Session. Moving a page also moves its preview, and the preview does not take host focus. Closing a host converts its retained preview into a standalone document tab without discarding unsaved content. Residency protection is calculated from the actually active host; hidden previews elsewhere in the same split do not substitute for a visible reference.
- **current (source)**: A Viewer contribution can declare `dockable` to make a page participate in workspace splits. Project files, the resource explorer, and new tabs reuse DocumentWorkspace's Dock placement, focus, and movement rules; they register page-tab identity only and do not create a document Session. Creation entry points in each leaf split explicitly pass the target leaf node, and choosing an existing page in a new tab reuses it only within that leaf. The leaf renders page content through the original Viewer registry. Document saving, shared Sessions, and residency policy remain with their original Owner. Real platform acceptance and screenshots are documented separately; passing them must not be inferred here.
- **current (source)**: A display-card contribution can declare `placement: after-artifacts`; it appears only after its turn completes successfully and after that turn's file artifacts. The assistant's `next-steps` uses this slot. A visible option or free-text input starts a new turn through the current conversation Composer's normal submission entry point, preserves existing drafts, and neither creates nor answers HIL. The old card becomes inactive after a subsequent user message appears, and duplicate submission is prohibited while sending; real client interaction still requires acceptance.
- **advisory**: Within a feature, SHOULD separate responsibilities by state/API/view, but small modules should not create empty shells merely for directory symmetry.

See [Preview architecture](preview.md) for the shared goals, startup isolation, data-consumption boundaries, and page-coverage criteria of the Web + mock scenario workbench used by product managers, designers, and frontend engineers alongside the real Electron app. The foundation is under implementation; integration of all pages and final acceptance are not complete. This does not change the existing Web/real Serve integration entry point, require a complete Store split first, or permit copying pages or scattering mock checks through business branches.

### Answer-format fallbacks

- **current (source)**: Markdown only classifies and displays the original answer; it does not write failure explanations back into the model response. Unknown languages use the original language name and plain text; incomplete tables retain the original text and show an explanation below the container; strict KaTeX and Mermaid each retain their failed source. Streaming turns communicate lifecycle through `pending`; incomplete fragments are not prematurely declared format failures.
- **current (source)**: `SourceBoundary` isolates synchronous rendering exceptions at both the code-block and whole-Markdown levels, preserving copyable source and an explanation while recording diagnostics. A failed code block does not remove adjacent body text, and rendering is retried when the source changes. Async resources and Mermaid remain the responsibility of their owning components; an error boundary does not replace async failure handling. The final source view still hides internal evidence-transfer annotations and does not execute model HTML or scripts.
- **current (source)**: Fenced code reads text from HAST and associates it with original ranges; it must not assume that React children remain strings after annotation decoration. Per-line mapping continues to use `SourceLeaf` boundaries, and displayed line numbers are excluded from copied text. Ordinary bare external links use semantic `Link`, single-line truncation, a full tooltip, and copy; citations, project sources, and conversation files retain their existing classification priority.
- **current (source)**: The business layer supplies Markdown image session-resource resolution and real file operations; on failure, the filename and action entry point remain. Policy-restricted external previews are distinguished from actual load failures. Authorized conversation images load in anonymous CORS mode and comply with the main window's COEP and existing backend CORS checks; cross-port `no-cors` blocking must not be mistaken for a broken image. This mechanism does not widen CSP, provide an arbitrary-URL proxy, or treat an action for a missing resource as a successful open.
- **current (source)**: An empty reply is determined from the effective body, answer card, or delivered artifacts of a completed whole turn; running, approval-waiting, errored, stopped, and unknown terminal states do not become empty replies. With no agent message, only an empty-state projection is shown; no persistent model response is created. Regeneration submits through the current conversation's Composer and is limited to the latest empty turn, idle state, empty draft, and queue state; it can be retried on failure. Subsequent user turns after success continue to prevent resubmitting a historical empty card; persistent idempotency is not established by an in-memory consumed set.
- **required**: A local formatting failure is not a model-service error. Do not automatically call the model to repair prose, modify original research data, or widen file permissions. A neutral empty result uses `Alert`'s `neutral` semantics; do not rely on a custom property competing with the default tone to override colors.
- **gap**: Source inspection and deterministic failure regressions do not prove acceptance across all native windows, themes, or platforms. Keep actual records and coverage limits in this round's acceptance plan; branches without evidence are not marked as passed.

### Settings persistence and quit barrier

- **current**: `src/persistence.ts` serializes preference submissions. `[preferences]` logs record `writerId`, `submissionSources`, `changedFields`, `submittedRevision`, and `acknowledgedRevision`. A revision is an in-memory sequence for this writer run, not a configuration-file format version; across renderer recreation, correlate it together with `writerId`. Fields record only top-level names, not setting values, document paths, model identifiers, or credentials.
- **current**: Save receipts retain the actual submitted values and version. The writer tracks automatic intent by field and generation; failures and reconciliation are handled by the same Owner, without adding configuration fields or an IPC protocol.
- **current**: Store projects UI language and selection prompts that take effect after confirmation only from save receipts/failure reconciliation. Local actions hold optimistic state for models, recents, editor options, shortcuts, and onboarding; a persisted snapshot is not fed back as new user intent. On save failure, preserve these local intents and the existing failure notice/explicit retry, preventing an old receipt from rolling back a new selection and triggering autosave again.
- **current**: On normal quit, first ask the renderer to freeze interactions, preference-state changes, and new submissions, then wait for existing saves and receipt application to drain. The main process validates the owning main frame, request ID, receipt version, and in-flight writes, then blocks later writes and stops the backend; Windows workbench-readiness and directory-write safety checks remain in place.
- **current**: A save failure or quit-barrier timeout cancels quit, restores interaction, and prompts the user to retry unsaved settings first. Successful reconciliation is not treated as a successful save; there is no unlimited automatic retry or silent dropping of failed intent. Drain is not guaranteed for forced quit, process crashes, or OS termination.
- **required**: macOS menu quit and Windows confirmation/tray quit both cover save-and-restart recovery; ordinarily hiding the window does not trigger draining. macOS results do not substitute for native Windows acceptance. Deterministic tests for delayed writes, save failures, stale receipts, and retry after cancellation supplement real interaction but do not replace real quit.

### Navigation telemetry

Navigation commits also generate a single non-persistent telemetry marker in `src/renderer/src/navigation.ts`. Store emits `[navigation]` from an effect after React commits, reusing the existing bounded console ring and main-process exact-prefix rotating log; it adds no history ledger, upload, or navigation decision. The field allowlist contains only source/action enums, an in-page sequence number, starting/current generation, before/after view/tab kinds, and boolean changes. It records no project/conversation/file identity, path, title, body, or stack.
`action` indicates only that a public action ran; it does not prove a DOM user click. Unattributed entry points remain `unattributed`. A batch records only its last actual commit; `evaluatedUpdates` indicates the number of coalesced candidate updates, while source and change booleans belong to the final candidate, so one log line cannot reconstruct all intermediate actions. Generations are for correlation only and do not add or change existing async fences.
This allowlist constrains only the new navigation records; it does not claim that all existing renderer diagnostics or logs are free of sensitive information.

### Conversation model selection

- **current**: When the user explicitly selects a model from the conversation model menu, the conversation-model command carries `remember_default`; an admitted service command persists the default before switching the Host at startup. The client verifies `default_model_id` in the conversation-model snapshot and no longer appends a default-value write during draining. With no bound conversation, the Store's target-preparation controller starts a preparation command bound to actor/model/UUID/service instance and saves the default. New conversations reuse this selection; browsing history shows only the model for that conversation and does not overwrite the default. Calls such as changing reasoning effort do not implicitly change the default model.
- **current**: If saving the default fails, retain the current local selection and show a retryable error. Reselecting the same model retries only saving the default and does not modify the conversation again. If model selection is rejected and not persisted, do not update the default; directory availability is still decided by the existing policy.
- **current**: All explicit new messages, including those in existing and restart-restored conversations, wait for target preparation to complete before creating a conversation, writing to outbox, or submitting a turn. The target is the current conversation's effective model and does not override the new-conversation default. Preserve the draft while waiting; changes to draft generation, project, model, service instance, context revision, or component lifetime invalidate the old send. For an unknown control request, query/recover only by the same UUID; do not replay the user message. Mounting, refreshing, and older receipts do not trigger message sends. The server prepares again before the open/turn business lease, closing the race between readiness and submission.
- **current (source)**: An ordinary send consumes only submission text that has not been edited and references that still belong to the original snapshot object. Text-edit revision is separate from navigation draft generation, so even clearing and retyping identical text does not consume a new draft. A known rejection restores only the text and references actually consumed by this send, preserving new input entered while waiting and new references with the same ID; unknown outcomes are not restored or replayed. Continue-planning and follow-up suggestions reuse the same submission entry point but do not consume unsent drafts or references.
- **required**: Present preparation failures separately from message-execution failures; failed or outcome-unknown messages retain the existing explicit resend/confirmation flow. Record real macOS and Windows product acceptance separately; contracts and static screenshots do not replace runtime evidence.
- **current**: Send preparation, the model menu, and the input error strip reuse the same preparation-failure feedback selector. Restart-required and unsupported receipts show their respective recovery guidance; if a request fails but its terminal state is unconfirmed, show an unknown outcome. Do not attribute every preparation failure to model connectivity. Parallel preparation callbacks from the model menu must not overwrite a known preparation terminal state with an error from saving the default. This feedback projection does not release the maintenance barrier, change recovery eligibility, or automatically resend a message.
- **current**: If the original preparation context is unchanged, a confirmed restart-required receipt remains as recovery guidance after a maintenance health probe temporarily loses the instance ID; losing the instance ID does not preserve successful admission. Clear the old receipt after confirming a new instance, switching accounts, or invalidating the original model/project/draft/conversation context. Backend and workbench availability continue to be projected independently from actual probes.
- **current**: In-progress and ready model-environment preparation states remain silent in the background, without a persistent prompt above the input. Show errors when preparation is rejected, requires a restart, or is unsupported. The semantics of waiting before send, rechecking admission, and not automatically replaying failed/unknown messages remain unchanged.
- **current**: If a shared Host rejects preparation because it is busy, the input tells the user to retry explicitly after the task ends, preserves the original draft, and shows no generic connection error. A busy shared host leaves the draft intact and asks the user to retry after the active task finishes; it never resends the message automatically.
- **current**: After startup navigation recovery is determined, lock one preparation intent to the service instance, wait for that instance's model catalog and conversation-recovery snapshot, then reuse the original preparation controller. Catalog responses carry their source service instance; reject missing or old-instance responses instead of relabeling them with the instance current when the response arrives. A restored conversation uses its persisted model; a new draft uses the current default without saving or rewriting the default. Invalid navigation produces no late preparation, and catalog refreshes and ordinary history browsing no longer create startup preparation. Give explicit feedback for a missing or disabled conversation model; do not substitute the default to warm up. Admission must still be checked again before sending.

### Conversation event recovery and diagnostics

-- **current**: `api.ts:streamEvents` resumes from successfully projected sequence numbers, deduplicates, and ignores callbacks from old connections; when idle, the server sends a named `heartbeat` event. After 60 consecutive seconds without a business frame or heartbeat, a sequence gap, or a synchronous projection error, request recovery for the owning conversation. When the window becomes visible or focused again, request recovery only if the current connection has exceeded the same activity window; keep recently active connections and already scheduled transport retries unchanged.
- **current (source)**: The conversation-body subscription in `live.ts` is limited to the current foreground conversation; its lease also constrains in-flight recovery, stale callbacks, and reconnects. On switching, close the old subscription first without stopping background tasks. A recovered conversation on the same instance resumes directly from the successfully projected body cursor without reopening Runtime on each switch. Still load the open conversation, history, plan, terminal state, and queue snapshot on first recovery, instance changes, sequence gaps, and projection failures. Handle snapshot failures with the existing bounded retry; do not treat an unavailable queue as empty.
- **current (source)**: Desktop conversation/project directories and background HIL, queue, and terminal summaries are read after invalidation through shared notifications. Summary sequence numbers compare only whether status is newer; they do not advance the body cursor or read watermark. PDF annotations and note sources reuse the same notification channel and refresh on domain changes, reconnect, and window focus, removing the previous fixed 2-second/5-second polling. Directory refresh shares single-flight behavior and one dirty reread, with bounded request timeouts. Snapshot requests are coalesced, failures back off independently, and instance resets discard old in-flight results. Web directory polling, independent execution streams, and temporary polling are outside this migration.
- **required**: Shared notifications signal invalidation, not a persistent event log; reconnect must reread snapshots. The body-subscription limit excludes existing independent streams such as file events, search, and generation, and does not promise connection reuse across multiple independent Desktop instances. Real-state acceptance must cover background completion/HIL, fetching missed body content after switching, PDF save/source deletion, and catch-up after disconnect; source and contracts alone cannot prove all these pass.
- **current**: `api.ts` derives `SessionTurnStatus` and recovery-snapshot validation from the same state set. `waiting` is a valid turn-progress state; when returning to a project, restore unanswered choice or permission cards and continue subscribing to events. Still reject snapshots with unknown states, incomplete identity, or contradictions about unknown outcomes; do not recover by automatically replaying interaction requests.
- **current**: Invalid recovery snapshots use the existing bounded five-attempt backoff retry. After exhaustion or when manual action is needed, show a reconnect entry point. Recovery failures and directory authorization failures describe only unavailable connectivity; retain the last known execution state and do not infer that the turn completed. Execution ends only on a successfully recovered trusted snapshot or terminal event. Reconnecting does not replay turns, tool calls, or submitted HIL answers.
- **current**: Structured `[session-stream]` and `[session-recovery]` logs go through main's existing rotating output to `$SCHOLARSEED_HOME/logs/window.log`. Correlate `sessionId`, `threadId`, `serviceInstanceId`, and `sequence` with backend `sse.connected` / `sse.disconnected`; inspect `reason`, `heartbeatCount`, `appliedCount`, `failedSequence`, `eventType`, `elapsedMs`, `queuedCount`, and `retry-decision`. Do not record frame bodies, user content, credentials, or exception messages.
- **required**: Comment-form `: keepalive` does not trigger native `EventSource.onmessage`; do not judge a healthy idle connection by the number of business frames. Heartbeats do not consume persistent product sequence numbers, trigger conversation projection, or write one log entry per frame.
- **gap**: Automatic recovery cannot determine whether a historical fault was a silent disconnect, background-window throttling, or business-projection failure. Retain original logs and attribute the cause using recovery reasons and cursor evidence. macOS and Windows use the same browser lifecycle and SSE protocol, but real window-recovery acceptance on each platform is not interchangeable.

The dependency direction is `app composition → feature public entry → contracts/shared primitives`; the shell consumes the registry and does not read private feature state in reverse. A feature MAY use shared business/primitive/UI; `components/ui` MUST NOT depend on a feature.

## Enforced by

Failure diagnostics for the shared API client are owned by `src/renderer/src/app/api/diagnostics.ts`:
`apiFetch` records HTTP status or transport failures; `getJson` / `postJson` add response-decoding failures.
If request-body serialization fails, `postJson` still returns `null` and sends no request; it records only the fixed classification
`request-serialization-error` and `status: null`, without reading or logging the body or original exception.
`[api-request]` goes through the existing rotating output to `window.log` and is collected in the feedback package only if the user selects runtime diagnostic logs.
Only allowlisted route categories, request methods, status codes, elapsed time, and fixed error classifications are retained. Unknown paths are hidden uniformly;
query parameters, dynamic IDs, request/response bodies, headers, raw exceptions, and stacks are not logged.
Browser network errors can only be classified; this cannot distinguish underlying causes such as DNS, TLS, or CORS.

Repeated failures are grouped by safe route category, method, status code, and error classification: record the first occurrence immediately, then count repeats for 10 seconds. At the end of the window, automatically emit a `suppressedCount` summary; emit it even if no later request occurs. Retain at most 64 groups and their timers, emitting pending counts before capacity eviction. If logs are selected, drain summaries before submitting feedback; do not drain otherwise. Do not filter all 401/503 responses. Content-operation polling retains only the fixed route category, not the operation ID. The security allowlist is not automatically synchronized with the full backend route table; adding a category requires privacy review.
The log prefix, timeout exception name, and four reviewed route constants are shared from `src/requests.ts`; callers and the allowlist reference the same route constants, so main does not depend on renderer in reverse. Draining uses a snapshot of group keys taken at that time; groups created during output keep their own summary window.

`scripts/ci/__tests__/standards.test.mjs` checks key dependency boundaries; TypeScript checks contribution contracts; adjacent unit/render/e2e tests verify domain behavior.
