# Built-in Browser

<a id="工作区页签"></a>

## Workbench Tabs

**current (source)**: Selecting the built-in browser from a new tab preserves that tab's identity and position and converts it in place, without adding another tab. Each browser tab is bound to a separate native webContents ID; navigation and back/forward history are isolated per webContents. The tabs still share the existing browser profile, so Cookie isolation is not claimed. Tab names follow the corresponding page title, fall back to the URL when no title exists, and use the localized default name on blank pages.

Closing an ordinary tab releases the webContents it owns. A page opened from search results is attached through its explicit identity. Agent reveal retains the existing session and target-generation checks; displaying an Agent page does not take ownership of it or close it. When a native webContents closes, its corresponding workbench tab closes too. WebContents IDs, titles, and icons are current-window state only; no cross-launch web-session restoration storage is added.

**current (source)**: In the non-editing state, long URLs are truncated in the address bar using regular weight; when focused for editing, the full value is retained.
The page favicon is read through normal fetch within that page's isolated world and the existing network boundaries. It does not bypass CORS, site CSP, private-network restrictions, or Renderer CSP; it sends no credentials and rejects redirects.
Only bounded raster images are accepted, up to 64 KiB. The default icon remains when no usable favicon is obtained.
The favicon result is checked against the webContents identity, URL, and current-turn origin; an asynchronous result from an old navigation cannot overwrite the new page's icon.

**gap**: Deterministic regression does not replace real acceptance of native-page tab switching, closing, titles, and icons. macOS evidence does not establish Windows acceptance.

## Product Switch

**current**: The manifest shipped with the product sets `features.browser` to `true` by default. An explicit `false` keeps it disabled; a missing declaration or a security fallback does not enable it. Only the strict boolean value `true` turns it on. The setting takes effect only after fully quitting and restarting Desktop. Development builds read `resources/product.json` from the app root; installed builds read `product.json` from Resources. This is not a user preference and differs from the browser Agent-use preference and CDP automation switch.

When disabled, the activity rail, browser workbench tab, and browser settings page are excluded from composition. Legacy navigation pointers project back to a safe page; existing browser data is not deleted. Main does not construct webContents, CDP, Agent transport, or suggestion/tooltip owners. IPC and the Serve browser/history bridge reject before reading state or replaying results. Legacy browser approval records display only a read-only explanation that the feature is disabled; they do not show dedicated authorization buttons or page/history-query content. The shared account menu and non-browser conversations retain their existing capabilities.

The product manifest enables `features.browser_agent_navigation` by default, allowing the assistant to open pages in an isolated tab belonging to the current conversation, subject to existing site rules; sites without authorization still require approval. `features.browser_advanced_settings` is off by default: the password vault, external CDP, and Agent site rules are hidden, and general reading, interaction, and history queries are unavailable. Existing explicit opt-outs and site rules are not overridden. Manual browsing, history, downloads, and product-search fallback are unaffected.

Web fallback does not provide the built-in browser. Desktop and managed Serve validate the same browser product switch through `/api/healthz`; an explicit mismatch, invalid declaration, or missing required field is reported as a startup error. When the feature is disabled, Desktop may connect to an older external Serve that lacks the field, but remote capabilities are unknown and the local browser remains fully disabled. This does not establish that an arbitrary external service has no browser capability.

**English:** The packaged manifest enables `features.browser_agent_navigation` by default. The assistant can open websites in an isolated tab belonging to the current session, subject to existing site rules and approval for sites without an authorization. Advanced settings stay off by default: the password vault, external CDP and site-rule settings remain hidden, and general Agent reading, interaction and history queries remain disabled. Existing opt-outs and site rules are preserved. Manual browsing, history, downloads and product search are unaffected.

**current (build policy)**: Main uses the official ws compile-time truthy flags `WS_NO_BUFFER_UTIL` / `WS_NO_UTF_8_VALIDATE` to eliminate optional native-addon detection while retaining JavaScript masking/unmasking, UTF-8 validation, and Node `buffer.isUtf8` when available. It does not depend on the user's environment, install an addon, or disable WebSocket/CDP features. Optional native acceleration is no longer used; performance parity is not claimed. macOS arm64/x64 and Windows x64 use the same non-native algorithm and host-validation selection, with no new addon ABI, signing, or unpacked dependency. **required**: Actual Main/preload must still pass the original complete module-closure checks and must not reference an npm addon externally; disabling the product switch does not replace compiled-closure verification. **gap**: Real builds/asar and binary/text CDP, plus normal password-vault UI/restart/screenshot acceptance, are separate for each target. Compilation and Node round trips alone are not product acceptance.

## Product Search Fallback

**current**: The product-bundled `web-search` uses the built-in browser through the private `search/browser` host bridge.
The resource search box performs official search and constrained fallback according to the [resource-search owner](../../../docs/features/resources.md). For the browser step, first open the Bing home page and obtain separate authorization for the regional site; wait 1 second, inspect the form, and enter the original query. Call native `HTMLFormElement.prototype.submit` through the host's fixed isolated world; do not dispatch Enter or build a URL for direct navigation. The form target remains frozen from the complete observation, but native `form.submit()` does not include the submit-button field.
Do not launch external Chrome, Edge, or Playwright Chromium, and do not use the user's persistent browser profile.
JavaScript is disabled on the private search page from creation to prevent preconnects from the home page or input events from exposing the query. The host's fixed isolated-world inspection and native form operation still work. Set `disableBlinkFeatures: AutomationControlled` only on the search-specific WebContents; do not use global startup arguments. Ordinary Agent and manual pages remain unchanged.
If the site depends on page scripts and cannot provide a compliant form or results, fail explicitly; do not re-enable page scripts automatically or bypass the guard.

This bridge is only for real turns of an active search Invocation and permitted Skill/profile calls. Its admission supports `ask`, `safe_auto`, and `bypassPermissions`, while still rejecting read-only or unknown modes and preserving the Skill's declared permissions and parent-permission limits. Requests accept no URL, CDP address, or arbitrary script; identity is not injected into the shared App Server or shell. The built-in search target remains nonpersistent, disables downloads and popups, is invisible to public CDP, and is precisely cleaned up at termination. When advanced settings are off, Desktop's private host transport accepts only scope control and product search, not general browsing or history-query actions.

**current (resource-result receipt)**: Browser-execution evidence received by the resource page accepts the host-supported `ask`, `safe_auto`, and `bypassPermissions` modes; it does not require upgrading the parent conversation to full permissions. Read-only, missing, and unknown modes remain rejected. Receiving results is not execution authorization: the Skill/profile, query, same-turn artifact-publication identity, and result contract are still checked. Site authorization and actual-side-effect checks remain with the original host.

Product search uses an exact HTTPS-origin allowlist declared by the search provider, and only for the real private search target. It does not read the legacy Agent Browser Use switch or site rules. Search-specific authorization covers one fixed GET form submission and does not call the ordinary-action approval API. Authorization is bound to the parent conversation/turn, target instance, policy revision, query, exact same-origin destination URL, and expiry. Revalidate the form structure, input, and submit control before execution. Before input, enforce request boundaries: reject POST, XHR/fetch/beacon, unapproved resources, and additional or cross-origin navigation; accept only one GET request to the frozen destination. Revocation, timeout, and unknown results are not retried automatically; the target is closed at termination. After submitting, request new authorization to read the results page; do not reuse home-page read authorization.

**required (regional home-page boundary)**: The host may consume a short-TTL, single-use receipt bound to the original request and target only after a real cross-origin home-page redirect from the controlled private search target has been blocked by the guard. The receipt proves that a redirect was blocked; it is not navigation authorization. A search may continue at most one home-page redirect between the provider's explicitly declared `https://www.bing.com/` and `https://cn.bing.com/`. The target must not contain `q`, URL credentials, or a fragment; Bing regional parameters other than `q`, such as `mkt`, may remain, so not all query parameters are forbidden. The host must obtain separate Navigate and Read grants for the complete target address. `cn` does not inherit `www` site permission; `ask/block` both stop the flow without changing site settings. This boundary does not apply to form submission: forms remain limited to one same-origin GET, and all submission redirects are rejected. Unknown navigation results without a valid receipt, expired/replayed receipts, or another regional redirect are not retried automatically.

**current (submission diagnostics)**: `browser-search` logs correlate execution stages by request/session/tab. `browser-search-form` records input validation, native form-submission `submit_issued/submit_ack` and `submissionAcknowledged`, main-frame requests, navigation, DOM readiness, and the first fixed-category failure reason. `browser-search-navigation` adds total request filtering, navigation guards, response codes, and provisional/load failure codes. Logs contain only fixed enums, boolean decisions, timings, and correlation identifiers; they exclude queries, full URLs, DOM, and raw CDP error text. If submission was issued but its outcome is unknown, the external result remains `browser_search_submission_unknown`; do not infer that the server did not receive it from an internal first failure or replay automatically. Record internal form timeout and cancellation separately; an outer bridge `timedOut=false` does not prove that the internal operation did not time out.

**current (rejection path)**: The form boundary always directly rejects non-main-frame resources and does not synchronously read site policy for requests that cannot be authorized. Aggregate rejection counts in terminal diagnostics to avoid repeated policy I/O and per-request logging that could block navigation completion during a resource storm. Recheck the original authorization, target, and revocation state immediately for main-frame requests, navigation, input effects, and DOM readiness. Do not cache authorization, extend timeouts, or allow subresources.

**current (private search rendering)**: The search-specific view stays natively hidden from creation, uses a fixed nonzero viewport, and disables background throttling for that WebContents. Renderer visibility or bounds messages cannot show the view or reduce its rendering dimensions to zero. Construction preferences do not prove that the current main frame is paintable after navigation: only the search view reapplies `setBackgroundThrottling(false)` at `dom-ready` and in the post-mount layout phase to synchronize hidden-but-painting state; do not skip this because a getter already returned false. `browser-search-render` records synchronization phase, native visibility, dimensions, and throttling value, without page content. Before input, wait for two rendering-scheduling cycles within the existing timeout, revocation, and identity checks, and record `render_wait/render_cycles` with dimensions and the native-focus boolean. Do not focus the window or WebContents, and do not enable page JavaScript. Two rAFs do not prove compositor submission; success still requires the exact GET request, navigation commit, and DOM ready. Electron throttling configuration affects rendering scheduling for windows in the same host, so do not retain this configuration object after closing the search target; do not change ordinary-page settings. Regression covers parent windows that have and have not been shown, as well as the home and result documents; it removes Playwright-injected overrides for `allow-pre-commit-input`, background rendering, and `disable-features`, and includes real-runtime evidence without a Playwright launch. Do not add a production-wide input-suppression bypass.

**current (results ready)**: After natural navigation commit and DOM readiness, wait 1.5 seconds. Within the existing identity, authorization, and cancellation boundaries, check every 250 ms up to 8 times. Return only when the URL and results-page input in the same document match the original query, the document is complete, the results container is visible and not busy, and result cards are stable for two consecutive checks. If `content-visibility` skips rendering a card, perform a fixed scroll on the bounded card only while both search-interaction and result-read authorization are valid, then revalidate and sample. Do not modify CSS, read hidden text, force a refresh, or semantically filter, reorder, or rewrite results. Record `homepage-settle/result-settle` during waits; still close the temporary Session at termination and do not persist or share Cookies. Improved parameters and waits do not guarantee Bing relevance; report real parameter comparisons and multi-query regression separately.

Reading uses a fixed isolated-world script and is limited to titles, links, and summaries in main-frame result cards. It filters hidden/inert content, sensitive inputs, and cross-frame content, and rejects an overlong link in full rather than truncating it; ordinary Agent AX output is not expanded. Other search providers, candidate artifacts, and the main search entry retain their existing contracts. When the product is disabled, authorization is insufficient, or the host is unavailable, fail explicitly rather than falling back to an external browser. Search on both platforms does not depend on Agent rule storage. If advanced capabilities are explicitly enabled, Windows rule persistence and Agent authorization need separate installed-product acceptance. **gap**: Real product acceptance of the new form path and evidence for target platforms must be verified independently; deterministic tests do not guarantee compatibility with the current Bing page.

**current (when advanced capabilities are explicitly enabled)**: The initial general Agent Browser Use configuration retains the two existing exact-source Bing presets. Other sources default to asking, and ordinary page submissions still ask each time. Existing v1/v2 policies are not overridden; corrupted or unsafe-to-read policy fails closed. These rules constrain general Agent browsing only, not product search.

## Open and Browse

The workbench's “新标签页” offers an “内置浏览器” entry that reuses the existing browser workbench and preserves current project context. Existing pages remain unchanged; when there is no page, show the existing address bar and guidance. Hide this entry when the product switch is off or in a Web fallback environment.

The browser has no entry in the left activity rail; browser settings remain available while the product switch is on. When a conversation requests a page, `browser/open` creates only an isolated blank tab and returns `tab_id`; it accepts no URL and does not access the public internet. Navigation then uses the existing `browser/navigate` and follows the original site-rule and approval flow. On successful navigation, Main sends the named web target; the browser feature validates the current conversation and target identity before showing the workbench. This does not launch the user's external browser, expose public CDP, or change site permissions.

`browser/close` accepts only `tab_id` and, under existing active-turn, private-authentication, and replay checks, closes a target created by that conversation through `browser/open`. It supports closing across turns within the same conversation and rejects manual targets, targets belonging to another conversation, and stale targets. Main holds the actual entry identity and transfers ownership only on a valid navigation commit; manual closing and host destruction clean up synchronously. This contract does not provide arbitrary UI dispatch or change navigation site authorization, conversation approvals, or external CDP preferences.

The browser appears in the workbench's top “浏览器” tab, with the page below the address bar; it is not a separate browser window. No internal web-tab bar or new-page button is shown. Manual browsing operates on the current page through the address bar, Back, Forward, and Refresh. Existing page targets and popup/Agent/CDP isolation remain unchanged. When there is no page, or the active page has an empty URL or `about:blank`, show usage guidance instead of covering it with a native blank page. Actual app exit destroys the page view; hiding the window temporarily hides the page, which remains usable after restoration.

The blank page shows only a globe icon and “输入网址，在当前工作台中浏览”; it does not show tutorial cards or example buttons. “更多浏览器功能” continues to use the isolated native dropdown menu with Find in Page, Print, Copy URL, Zoom, Developer Tools, History, Clear Browsing Data, and Browser Settings. Zoom controls use equal-sized icon buttons; hovering over Reset shows “重置缩放”. The clear-data entry points to the existing data-cleanup area in Settings and does not clear data directly; the user must still choose a scope and confirm.

The address bar accepts complete `http://` / `https://` addresses; for a plain domain, it prepends `https://`. It rejects non-web protocols such as `file:`, `javascript:`, and `data:`. Private-network addresses are inaccessible by default. Temporary authorization is granted to a page tab only when the user explicitly enters a same-origin address matching the current ScholarSeed service's `apiBase`; page redirects or CDP cannot broaden this authorization.

Web popups do not open separate system windows. Allowed destinations opened by public websites appear in built-in tabs, with at most 8 popup tabs retained at once; excess requests are rejected. This limit does not apply to tabs created manually. Failed loads clean up their temporary tabs. Closing or replacing the source page cancels only popups that have not finished opening; pages already converted to independent tabs remain. Popups initiated by a local `apiBase` page are always rejected and do not inherit the temporary local access granted through the address bar.

Closing or replacing the source page cancels pending popups only. A popup promoted to an independent tab remains open and keeps its quota slot until that tab closes.

## Playwright CDP

This section describes behavior when advanced capabilities are explicitly enabled; the product does not create an external CDP listener by default.

“Settings → Browser → External Browser Automation (CDP)” persists through Desktop `RendererPreferences.browserAutomationEnabled`. It is enabled on first use when no explicit setting exists; an existing valid boolean is preserved, and the user's choice persists across restart. A corrupted record or invalid explicit value does not grant access based on the default. Ordinary renderer preference saves preserve the disk-authoritative value; only the narrow browser-toggle save path changes it. This toggle does not control `features.browser`, Agent site authorization, or product search. The settings page shows the local listening address and provides “Copy CDP Address”. **The complete address is written only to the operating system clipboard** and includes a token generated for the current startup; the settings page shows only `127.0.0.1:<port>` without the token. Local programs holding the address can read and interact with built-in webpages that are allowed to be exposed; the product's main UI is not exposed. Treat the complete address like a temporary credential; do not put it in logs, screenshots, or the code repository. The service binds only to local `127.0.0.1`; the address becomes invalid after disabling, quitting, or restarting. Protocol and webpage-target restrictions, private Agent/search target isolation, and DevTools mutual exclusion remain unchanged; this does not expose Electron's full debugging capability.

```ts
import { chromium } from '@playwright/test'

const endpoint = process.env.SCHOLARSEED_BROWSER_CDP_ENDPOINT
if (!endpoint) throw new Error('先在 Desktop 复制 CDP 地址并设置环境变量')
const browser = await chromium.connectOverCDP(endpoint)
try {
  const pages = browser.contexts()[0].pages()
  const page = pages.find(candidate => candidate.url() === 'https://httpbingo.org/forms/post')
  if (!page) throw new Error('先在内置浏览器中打开目标网页')
  console.log(await page.locator('form').textContent())
  await page.getByLabel('Customer name:').fill('ScholarSeed CDP')
  await page.getByLabel('Medium', { exact: true }).check()
  await page.screenshot({ path: 'browser-page.png' })
} finally {
  await browser.close()
}
```

CDP exposes only manually browsed tabs in the product's built-in browser. Agent-isolated tabs do not appear in the target list. When a manual tab switches to Agent context, its existing external CDP session is invalidated immediately. The connector does not expose the ScholarSeed main interface, global Electron targets, or other application windows. It implements a restricted browser-level CDP subset and verifies only the capabilities needed by the currently pinned Playwright `chromium.connectOverCDP()`; it cannot create arbitrary targets, download files, change permissions, or access unregistered targets. The webpage remains subject to the browser's address, network, permission, and download policies.

## Browser Settings and Data

“Settings → Browser” is a separate top-level settings page. Browsing history records only public webpages that opened successfully and is stored in a separate browser database under the product user's home directory. Local temporary-service pages, the main interface, and Developer Tools are not recorded. History can be searched, paginated, reopened, or deleted entry by entry, and remains available after Desktop restarts. Chromium stores webpage cookies, cache, and site data in a dedicated persistent partition isolated by the current product home; it is not shared with the main interface or credential Session. Due to Electron storage constraints, the partition files are under system-level `sessionData/Partitions`, not in the browsing-history database.

Cleanup can target the last hour, last day, or all history; a specified site; all data; or selected types among history, cookies, site data, and cache. Site- or type-based cleanup affects only persistent sessions used for manual browsing. Local temporary pages and Agent's separate nonpersistent sessions are unaffected, even when they use the same site. Because persistent webpage tabs share a Session, site data could be recreated as a third-party resource by another top-level site. Therefore, cleanup closes **all** tabs in that persistent Session and revokes Agent authorization for those targets; unaffected isolated sessions may continue navigating. Clearing all history and site data still closes every browser page and nonpersistent session. History-only cleanup does not interrupt an Agent navigation in progress. Type-based site-data cleanup supports only all time; the time range applies **only to history**, because Electron cannot clear site data by time range. When clearing cookies for a specified site, Electron may include other subdomains under the same registrable domain. CDP is disabled before site-data cleanup. Already downloaded files are not deleted.

The Downloads section shows the current directory and lets users change it or restore the system default through the system folder picker. “Ask every time” uses the system Save As dialog. macOS automatic mode is available only when a real `fclonefileat` capability probe succeeds for the destination directory: downloads are written to Main's private staging area, then published by an atomic clone through a pinned directory handle, with symlinks blocked and an exclusive filename. On cross-volume destinations or when cloning is unsupported, “Ask every time” remains selected. The capability is rechecked if the directory changes, and failures are closed safely without overwriting existing files. The attempted publication state is persisted first. If a crash or later error makes the outcome uncertain, the staged file is retained and the user is prompted to open the directory, delete it, or handle it later; it is **not automatically resent**, to avoid duplicates. Interrupted partial downloads are retained and recorded so another instance will not mistakenly delete an active download at startup. Windows currently lacks an equivalent safe publication boundary, so automatic mode cannot be enabled. Download sources in built-in webpages are constrained by navigation and network policies: a `blob:` download is allowed only if the URL remains unchanged throughout the chain, its creation origin matches the top-level page, and its inner origin still satisfies network policy. `data:`, opaque origins, cross-origin downloads, and mixed redirect chains remain rejected. This check does not establish cross-origin initiator identity, so it cannot be broadened to arbitrary `blob:` downloads. CDP cannot rewrite download policy. Download-behavior settings sent by Playwright on connection receive only a protocol-compatibility response and do not bypass product download policy.

The Agent site-rules section manages `ask`, `allow`, and `block` policies for reading and interaction by exact HTTP/HTTPS origin. Deleting a site's rule revokes both authorizations at once and increments the policy revision. These rules apply only to Agent Browser Use; they do not change manual browsing, device permissions, external Playwright CDP, or network isolation. The product routes currently include `list`, `snapshot`, `read`, `navigate`, `interact`, and `submit`. Once Agent Browser Use is open, it can list registered tabs. Reads require authorization under the target site's rule; navigation requires separate authorization for the complete normalized destination URL, and approval cards distinguish the source page from the destination site. Clicks, typing, and submissions each require HIL confirmation; a persistent interaction rule does not replace approval for an individual action. Approvals, denials, revocations, tab recreation, and external navigation are constrained by session/turn, target instance, and policy revision. If an issued action has an uncertain outcome, it is recorded as `unknown` and is not retried automatically. These routes and deterministic tests do not amount to acceptance of a real model turn and HIL. **current (source)**: macOS and Windows use the same Desktop synchronous policy persistence. Each authorization reads from disk; reads and writes share a mutex keyed by home identity, and writes check the revision under the lock before atomically replacing data in a verified directory. macOS writes also hold the legacy directory lock. **required (real-device acceptance)**: Verify settings read/write, persistence across restart, and immediate revocation on both platforms; verify actual Agent authorization in an installed Windows build.

Agent `snapshot`/`read` output is **restricted, redacted AX-exposed content from the main frame**, not a screenshot or “only text visible to the naked eye.” Transparent, off-screen, or same-color text accessible to a screen reader may still appear. DOM `hidden`/`inert`, AX-ignored content, sensitive inputs, and cross-frame sources are filtered; password values cannot be read back. Webpage content is always untrusted and cannot serve as Agent instructions; approval cards warn about read risks. Agent navigation uses a separate nonpersistent webpage Session and does not inherit the manual tab's login state. Downloads are always disabled for that Session. Other manual tabs continue using their existing Session, and Agent navigation does not disable their downloads. This isolation and rejection of late downloads have deterministic tests, but still require real Agent product-flow verification on macOS and Windows.

Main-frame AX reads are not truncated at a fixed depth; the returned tree remains bounded by node, byte, and snapshot budgets. Descriptions for the same DOM node may be shared within one snapshot, but subsequent reads and every action phase recheck live authorization, target, AX, and DOM state. An action does not treat changes to the displayed `class` or `style` attributes as target replacement; all other attribute comparisons, hidden/sensitive/cross-frame filtering, and AX identity checks remain unchanged. Style changes caused by focus do not bypass these checks. Stale references require a fresh snapshot and normal approval; an unknown result from an issued action is never retried automatically. If native approval has not yet been registered, the execution side waits only for approval of that same prepared action; cancellation, revocation, or expiry still invalidates it.

Action results are separate from effect convergence. If an issued action causes navigation, old references become invalid immediately and no further Input may be sent; the business result may remain `unknown`. Native transport is retained only until passive observation completes. Convergence must confirm the same webpage instance, debugger, and main-frame network/loading completion plus a quiet period. It does not depend on the old document's origin/generation remaining constant and grants no read or execution authority over a new document. Revocation, detach, instance/main-frame replacement, overflow, timeout, or continued loading prevents convergence; a business error alone does not invalidate a barrier whose completion has been confirmed. Subsequent turns still pass through the original scope/end, replay, and approval boundaries.

Registry invalidation notifications distinguish native document navigation from authorization revocation while preserving the existing target/external ownership checks. Navigation synchronously invalidates old grants, snapshots, and prepared actions. The original transport is retained only when side-effect observation is already in progress; without an observer, it is released immediately. Explicit cancellation, data clearing, closing, manual navigation, and debugger loss do not use this passive-retention path and still trigger full revocation.

After effect convergence fails, ordinary operations and subsequent scopes remain frozen. The currently valid turn may still revoke private targets owned by this session through `browser/close`. Closing uses the original authenticated loopback channel, a separate bounded replay partition, and monotonic identity checks for the same instance. It does not clear old frozen records, restore read/execution authority, or automatically retry a submission. The shared Host fault marker remains. Requests continue to be rejected when the product is disabled, the channel is missing, or the target is manual or belongs to another session. Successful closing proves only that resources were revoked; it does not prove that the earlier submission succeeded.

Partial scope-finalization nonconvergence is distinguished from channel failure. While the original scope remains frozen and the host can confirm it, Main returns HTTP 408, `scope_unsettled`, and one of the fixed phases `requests`/`effects`/`leases` for a local drain timeout or explicit side-effect fence. Serve keeps the shared client usable only for responses matching the scope/end, status code, and phase; Main still rejects the original scope and does not restore its authorization or unknown actions. Unknown exceptions, cancellation, lost responses, host exit, and invalid responses continue to fail closed. After waiting for a phase, the original scope identity and transport state are rechecked. Once the Agent exits, it cannot issue a “partially unsettled” proof.

Native clicks round the layout center before performing main-frame hit testing, and dispatch the mouse event at that same coordinate. A rounded coordinate that hits an adjacent node is still rejected; fractional layouts are not accommodated by skipping hit testing.

Snapshot budget failures return `browser_snapshot_too_large` or `browser_snapshot_timeout`, making clear that no webpage action was dispatched by this read and preventing a read failure from being misreported as an unknown submission result. Arbitrary exception details are still collapsed into safe errors; late results after authorization changes or disconnection are not forwarded. Snapshot budgets, approval, and cleanup mechanisms are unchanged.

Stale references and invalid read authorization in ordinary reads and snapshots return `browser_stale_ref` and `browser_read_authority_invalid`, respectively. The fixed safe classification is forwarded only while the current identity remains valid and the channel is connected; timeouts, interruptions, and unknown results from dispatched interactions are not rewritten. When guidance requires observing again, current site authorization and approval still apply; revoked permissions cannot be restored, old actions cannot be reused, and actions are not replayed automatically.

The Agent Browser Use Serve→Main channel is provided by [Main transport](../src/main/agenttransport.ts),
which binds only to local `127.0.0.1` and generates an independent random key for the managed backend lifecycle.
[Backend startup](../src/main/backend.ts) passes the port and key only to that subprocess;
the [Serve client](../../serve/service/chat/service/browserhost.py) removes both from its environment at startup.
It does not reuse the Main→Serve host key and is not a CDP endpoint for external Playwright.
Changes to this boundary must check source authentication, session/turn, replay, and revocation together; a loopback address alone is not authorization.

## Primary Password Vault: Source Integration and Acceptance Boundary

This section describes behavior when advanced capabilities are explicitly enabled. By default, the product does not initialize the password vault or its fixed-storage helper.

- **current (source)**: The password-vault card in Browser Settings opens a separate trusted local view through a secret-free ordinary bridge. Creation, unlock, manual locking, and protected deletion confirmation are handled by Main `VaultOwner` through the generation port of the same fixed Store consumer. The ordinary renderer, webpages, menus, and Python helper do not receive the master password, keys, or plaintext entries.
- **current (source)**: v1 uses the complete original 60-byte header as AES-256-GCM AAD, fixed async scrypt N=131072/r=8/p=1, a 32-byte salt/key, and 192MiB maxmem. Each encryption uses a fresh 12-byte nonce and a 16-byte tag; the complete file is limited to 8MiB. Bounded UTF-8/JSON/schema parsing occurs only after authentication. The process-wide single KDF slot is released only when the native callback finishes; logical cancellation on blur cannot physically cancel scrypt.
- **current (source)**: A new master password must contain at least 12 Unicode code points and no more than 1024 UTF-8 bytes; lone surrogates are rejected, while spaces and character combinations are preserved. Unlocking an existing vault does not apply the creation minimum. Wrong passwords, corrupt vaults, and unknown storage results do not cause recreation. Deletion is bound to a fresh observation digest; cancellation writes nothing, and a conflict preserves the winner.
- **current (source)**: Normal public dev/build generates an independent `out/protected/<generation>` renderer/preload/fonts bundle and manifest before Electron starts, bound to a Main-compiled literal. Main and the ordinary preload load source from the same frozen bytes; loading, transformation, and output-inventory checks reject mixed revisions. The independent overlay/menu preload uses the same snapshot. Build inputs such as `package.json` are also included in the exact source inventory and byte digests. Changes after freezing still cause compilation to be rejected; other unregistered local dependencies are not allowed. Missing or extra inputs, hash mismatches, and stale generations are rejected. Protected sources are not hot-updated: stop and restart normally after changes. Explicit build watch rejects only protected capabilities; ordinary HMR/watch is unchanged.
- **current (source)**: If an ordinary lock revokes the initial read-only availability observation of the fixed vault, the same live Store may perform at most one fresh observation. Probes are deduplicated for the same Store, and restoring focus permits a governed re-observation. Recovery projects only locked/uninitialized state; it does not restore keys, metadata, or old prompts. Unknown mutations, debug/asset invalidation, and retired Stores do not auto-recover.
- **required**: The vault may be used only through the normal entry point without global, Node, or product debugging. Recheck actual Node inspector and product/protected DevTools/debugger state before operations and after every wait; restricted CDP for ordinary webpages remains available. Window blur/hide/minimize, screen lock/suspend/resign, renderer crash/navigation, backend/window revocation, and before-quit (including an early return blocked by update) all synchronously lock it. Reliable erasure of JS/IPC/OpenSSL copies cannot be guaranteed; detection of malicious native injection by the same user is not promised.
- **gap (acceptance)**: Deterministic crypto tests, the real isolated file helper, IPC admission, and the standalone builder are not product acceptance. Real UI flows on macOS and Windows for a normal non-debugging user—Settings → create → lock → wrong password → restart/unlock → delete—along with focus/screen-lock behavior, packaging/native-file recovery, and final screenshots remain to be verified. T9 credential Sessions, T10 import/management/fill, and T11 system-dialog integration are not implemented; no placeholder actions are shown.

<a id="为什么不能只调-css"></a>
### Why CSS Alone Is Not Enough

The browser webpage is hosted in main's `WebContentsView`, not in the main renderer's DOM. `z-index`, React portals, and absolute positioning can change only the main renderer's paint order; they cannot cross native child-view layers. When product overlays such as address suggestions or Tooltips intersect the webpage, they need a trusted native view at a higher layer in the same window. Do not simulate coverage by hiding, shrinking, moving, or replacing the webpage with a screenshot.

The real defect on 2026-10-08 illustrates this boundary: the bottom of the left-side “文献全览” (Literature Overview) tooltip was at 155 CSS px, while the webpage began at 152 CSS px, an overlap of only 3 px. `viewport.ts` treated an intersecting Tooltip as full occlusion and sent `visible: false`, so main hid the entire webpage. The site loaded successfully and its content was not itself broken. Moving the tooltip, adding an overlap threshold, or ignoring all Tooltips would not solve this composition problem.

<a id="所有权与不变量"></a>
### Ownership and Invariants

- **required**: The shared presentation model is validated by the Desktop contract. Main's overlay owner handles sender/frame identity, isolated Session, local-resource allowlist, native layering, zoom clipping, and destruction. Renderer handles tooltip text, theme, language, and anchor measurement; it does not pass HTML, scripts, arbitrary URLs, or system operations.
- **required**: Address suggestions and display-only tooltips use separate lifecycles and revisions. Showing or dismissing a tooltip must not revoke address suggestions, option mappings, or focus requests. Native tooltips do not take focus, contain no focusable actions, and are not browser tabs, history, downloads, Agent, or restricted CDP targets.
- **required**: Only noninteractive text tooltips that satisfy the native presentation contract may be excluded from full occlusion checks, and native presentation must be requested synchronously. Do not wait for asynchronous presentation before restoring the webpage, or the webpage will remain hidden for a frame on the first hover. On presentation failure, report the error and retain the DOM tooltip; do not claim the overlap is displayed correctly. Do not globally remove occlusion protection for dialogs/menus/listboxes or complex tooltips; modal dialogs must still prevent native webpages from covering product interactions.
- **required**: Distinguish the tooltip content rectangle from its painted rectangle, which includes the theme shadow: the native view covers the painted rectangle, while internal content stays positioned in its original content rectangle. Do not use a transparent full-window overlay. Both the native background and the tooltip renderer's page background must be transparent, or rectangular color will show around rounded corners and shadows. Electron `WebContentsView` does not support the mouse pass-through behavior of `BrowserWindow.setIgnoreMouseEvents`; even a small shadow boundary may receive mouse input. Do not claim `pointer-events: none` passes input through to another native view, and do not replay clicks to the underlying webpage to compensate, since that could trigger unintended actions.
- **required**: Dismiss the corresponding tooltip when the pointer leaves its trigger, the module/tab changes, the window loses focus or is hidden, or the view is destroyed. Late load or IPC callbacks must not revive a stale tooltip. Preserve the main renderer's accessibility description relationship, reuse the product Tooltip theme semantics, and do not inject product UI into webpages.

### Review Path for New Overlays

**current (source)**: Citation previews and source lists explicitly opt into
`PortalProvider.renderOverlay` with `hosted`. Workspace reuses the bounded native
conversation host for popup content only, leaving conversation state, drafts and
web pages in place. Other popups and the occlusion safety fence remain unchanged.
Cross-document overlays track their original anchors and support Escape, outside
clicks and focus restoration. Cancelled initial hovers finish the hidden host's
paint handshake without reviving stale content.

The source explicitly selects `hosted` via `PortalProvider.renderOverlay` for this preview and source-list path.

**current (source)**: Browser `operation_failed` and more-menu failures reuse the global Toast,
without inserting an Alert below the toolbar. A title-only Toast intersecting a webpage is
projected by the existing native-tooltip owner using the UI Toast appearance. Dismissal and
hover/focus pausing are forwarded only to the original Toast; timing, deduplication, and queueing
remain with the original UI owner. Toasts containing descriptions, business actions, or complex
content are excluded from this plain-data projection, and the existing occlusion protection is
not relaxed.

**current (source)**: When DevTools is docked in the main window, the window content size differs from the product renderer
viewport. The menu owner reads the product's actual viewport with bounds in an independent
isolated world and validates the current frame, window size, zoom, lease generation, and projected
dimensions, while preserving sender, target, and focus checks. Do not bypass validation by
increasing tolerances or allowing arbitrary smaller viewports. Without DevTools, continue using
the native window size. Deterministic regression does not replace real-window acceptance on macOS
and Windows.

First determine whether an overlay intersects the native webpage rectangle, then decide whether it is a noninteractive tooltip, an interactive suggestion, or a modal panel. Reuse the existing overlay owner and `components/ui`; do not create a CSS exception or another browser window for a single entry point. Changes must check the shared protocol, main/preload identity boundary, renderer lifecycle, and `viewport.ts` occlusion classification together.

Regression must use the real Desktop to hover or keyboard-focus the entry point, compare the webpage's native `bounds`, `visible`, page `innerWidth/innerHeight`, and scroll position before and after the overlay, and check for leftovers after pointer exit and repeated switching. Screenshots must show the native composition of the same window; a screenshot of only the main renderer or webpage cannot prove correct stacking. macOS results do not constitute Windows acceptance; record each platform's status and outstanding work separately.

When reusing the Tooltip visual component, main has already set the native view's absolute position, so do not apply the component's anchor offset again inside the overlay. Tailwind 4 `translate` is an independent CSS property; `transform: none` does not clear it. Screenshot review found that a 68 px-wide tooltip was still shifted left by 34 px, clipping its text. Clear the inner offset as well and verify that the content rectangle fits entirely inside the native view. Do not mask this issue by changing the view width, waiting more frames, or merely asserting that text exists.

`getBoundingClientRect()` excludes `box-shadow`. Creating a native view sized only to the tooltip's 68×30 px content clips the theme shadow, making its lower edge appear covered by the webpage. Any added paint bounds must come from the actual theme shadow; do not add webpage padding or change the content anchor. Acceptance must check not only complete text but also rounded corners on all sides, shadow, transparent regions, and clipping at the window edge. If the window loses focus or the native owner is revoked during a screenshot, mark the screenshot invalid; a `visible` assertion made before capture cannot substitute for the state during capture. Evidence from a real focused window and ordinary behavior regression are distinct evidence types.

### Interactive Menus: Single Business Source and Paint Acknowledgement

**Current (source)**: With the browser enabled, an isolated container preloads without a menu model. Normal dismissal of a loaded browser menu hides the container and clears its model. Reopening reuses the container, but issues a fresh session/revision and requires a new paint/focus acknowledgement. Cached rendering grants no action authority. Navigation, identity/target invalidation, crashes, timeouts and window disposal release it. Loading failures retain resource restrictions and permit a later retry. The `resources-ready`, `renderer-created`, `loaded`, and `renderer-acquired.warm` logs distinguish initialization cost from reuse; opening before preload finishes can still wait for loading.

The menu is not a plain-text Tooltip, and the product DOM Popover cannot be reused directly while a native webpage is visible. `src/main/menuhost.ts` owns the interactive overlay and real-window eligibility; `src/menu.ts` validates the bounded model and fixed actions; preload exposes only the narrow menu channel. Main's `presentation()` / `subscribePresentation()` projects a monotonic revision based on actual webpage visibility. An ordinary menu may be mounted only when inline eligibility is explicit; seed, publish, or focus failures must not silently fall back to a DOM menu obscured by the webpage.

`components/primitive/presenter.ts` is the actual owner of the shared coordinator. Browser and account consumers hold their own surface-scoped handles; disposal, updates, and revocation affect only their own lease. Do not create another global presenter for a new menu, because an old consumer's dispose or late failure could close a newer consumer's menu. Replacement, navigation, identity changes, and window lifecycle events must all prevent an old lease from being revived.

Account data is requested only from the original business host: `components/business/AccountMenuPanel.tsx` receives a redacted, plain view and does not call account APIs or read the Store. The ordinary menu and native renderer use the same Panel. Identity cards and action rows reuse the UI Menu keyboard semantics. Language is a same-document submenu; the submenu consumes Esc first, and a second Esc closes the root menu. Login, Settings, Feedback, and cloud navigation close the menu before calling the original host. Sign-out failures retain the error and retry capability; language confirmation for a dirty editor still uses the original Store guard.

**A paint ACK does not prove that the view is synchronized.** Native seed, initial loading, and paint confirmation are asynchronous, and points, busy/error state, language, or theme may change during that time. The host must retain the latest desired snapshot and, after the initial ACK and each update ACK, serialize and deduplicate updates for the same valid lease. Do not ignore an earlier change merely because `presenter.current()` is non-null when a later update arrives. Check the current opening, identity, and menu generation both before and after resending, so a late result from A cannot overwrite B. Do not hide the race by reopening the menu or manufacturing a business-state change.

**current (menu paint scheduling)**: After the menu document loads, attach it to its window in a natively hidden state, then synchronously disable background throttling so hidden documents can also receive render scheduling on Windows. Attachment does not mean display or authorization: before paint ACK, keep `getVisible() === false`, do not focus, and do not execute actions. After a valid ACK, recheck the window, target, geometry, and generation before showing it and confirming native focus. On failure or revocation, remove the view through the existing lifecycle. Do not replace this state transition with early display, forced focus, a fabricated ACK, or a longer timeout. Compiling the native menu contract on both platforms does not replace real product acceptance of menu, theme, and window interactions.

**current (resource layout)**: Main's `applicationRenderer()` resolves the resource root for ordinary renderers and native menus/tooltips consistently: development uses the checkout's `out/renderer`; installed builds use `renderer` under application resources. Windows does not use resources from a standalone Electron engine. Overlays continue using a closed file manifest and isolated preload; do not restore a duplicate renderer removed from app.asar or relax network/navigation permissions.

Deterministic regression must cover deferred seed, business updates before the initial and subsequent paint ACKs, and ensuring old results are not resent after replace/dispose. These tests prove only code interleavings, not native composition, focus/DPI, or real account security. An account renderer epoch also does not prove Main/Serve credential isolation; conditional clearing by the authentication owner and real acceptance on both platforms are separate gates.

Boundary index: [ownership rules](architecture/ownership.md); real verification requirements: [testing and acceptance rules](quality/testing.md). Targets and probes from historical proposals do not prove current product acceptance; the migration boundaries below still need to be closed independently.

The page controller in `src/main/page.ts` attaches to the existing BrowserEntry; BrowserRegistry remains the sole source of tab and WebContents identity. Actions capture `tabId/instanceId/navigationId` and the active generation, which are rechecked during execution, asynchronous callbacks, and projection. A→B→A must not revive an old request. FindPanel reuses the shared Popover/Input/IconButton. Opening and closing preserve the webpage's native position, size, and runtime state; executing a search may scroll to a match. The first outside click only closes the panel and is not forwarded or replayed to the webpage. Esc returns focus to the webpage or More button according to the entry point; blur and outside clicks do not steal focus. Initial paint/focus ACK is separate from subsequent result updates, and count or theme repaint must not remount the input or reclaim focus from the first item.

The handle on the left of the find box uses Pointer Capture for dragging and reuses the Popover's viewport-edge clamping. Dragging changes only the overlay's internal position, not the webpage's native bounds. The result count, previous/next controls, and close button appear in one row. Zero matches show `0 / 0`; close or Escape clears highlighting through the native owner's `stopFindInPage('clearSelection')` and leaves the webpage in place. Result/theme updates within the same find session preserve position; a new session resets to the toolbar anchor.

Actual results come from `found-in-page` and are filtered by target, lease, querySequence, and Electron requestId. An empty query is invalidated before stop; waiting is not represented as zero matches. For the pinned Electron 44.3.0, `findNext` maps to a new query session as follows: true for a new term, false for previous/next on the same term. On upgrade, recheck the pinned version and actual matching behavior instead of inferring semantics from field names.

Set `isolated` before the first zoom navigation. Same-origin tabs may share a Session but do not share zoom levels. A staged page inherits the old page's zoom; promotion rereads the old page's latest value. Zoom is stored in tab memory only. `pageZoomSteps` in `src/browser.ts` is the sole owner of step selection: factor→level→factor round trips have floating-point error, so narrow near-step comparisons are used only for previous/next, reset, and boundary checks. They do not write back the zoom, alter the actual displayed readback, or round arbitrary out-of-table values to a step. Main still accepts only exact factors from the configuration table. Regression covers positive and negative conversion noise at every step, upper/lower boundaries, reset, and truly out-of-table values, preventing a step from selecting itself again or accidentally enabling zoom above 500%.

After system printing is submitted, it uses a separate page operation and does not depend on the menu's short-result lease. Exact cancellation reasons are distinguished from failures; losing focus to a normal OS dialog does not pretend that submitted work was cancelled. Navigation, destruction, or a crash only invalidates the old UI result and releases the local wait; it does not claim to undo physical printing or confirm that paper was produced.

These design constraints are in source and have received focused review; they are not proof of product acceptance. Find IME/focus, keep-open during horizontal zoom, full-step readback across two real same-origin pages, printing, and DevTools/CDP mutual exclusion must be exercised in final macOS/Windows Desktop builds and checked in native-composition screenshots. Component or pure-port tests are not substitutes. Device-toolbar support and safe screenshot publication remain separate capabilities to close.

<a id="固定浏览器存储权限与恢复边界"></a>
### Fixed Browser Storage: Authorization and Recovery Boundaries

Fixed product files and user-selected external files represent different authorizations and cannot share an IPC that writes to arbitrary paths. `service.paths` declares the user-level browser directory and adds it to the Agent file-access denial scope; `service.cli.browser` accepts only the `vault` and `downloads` kinds. Main's `vaultstorage` starts a binary-pipe helper using the actual backend's Python, cwd, environment, and profile projection. It does not go through Serve HTTP or return ciphertext or paths to the ordinary renderer. When the browser is disabled, configuration blocks all storage side effects before the factory runs; old data is neither read nor deleted. Attach is explicitly unavailable if the trusted local projection is missing.

After every asynchronous wait, Main rechecks the window, backend, and owner generation. Exit, backend replacement, or helper EOF revokes availability; late results cannot restore an old owner. The Python owner projects versioned budgets through a handshake. Main accepts them only after validating strict field types, duplicate keys, budgets, and independent hard limits; arrays cannot masquerade as protocol state through string conversion. This consumption establishes storage availability only; it **does not mean password-vault or download-directory functionality has migrated**.

Concurrent writes use a stable OS lock and expected-digest CAS to protect cooperating product writers; they do not claim to prevent a malicious process running as the same user from modifying arbitrary files. Each kind permits at most one active transaction. File changes begin only after `attempting` is persisted, and the next transaction is allowed only after a terminal state is persisted. A bounded terminal-record set with a retirement watermark ensures old cleanup touches only bound objects and does not reclassify an old operation based on a new final file. Deletion recovery uses a bound tombstone. Corrupt or unknown state is retained and fails closed; the system cannot automatically retry publication, delete unknown files, or roll back a newer successful commit.

macOS uses pinned directories, no-follow, private permissions, and directory synchronization. Windows uses RootDirectory-relative handles, rejects reparse points, applies a restricted DACL, and defines native/CRT ownership explicitly. A Windows file flush does not provide strong directory durability against sudden power loss. Recovery tests pause real operations through a test-side pipe checkpoint rather than treating POSIX `select`/`SIGSTOP` as cross-platform mechanisms; test control logic is not included in the production helper.

The source and focused contracts above have been reviewed independently. Windows native behavior, post-build product off/on/off, attach/restart, and final screenshots remain to be accepted. External publication of screenshots and downloads is a separate boundary; passing fixed-Store tests cannot substitute for it or establish delivery of complete browser-storage functionality.

<a id="受保护输入的资源-custody"></a>
### Resource Custody for Protected Input

Within one owner, `main/vaultipc.ts` distinguishes an available presentation capability from a view/session that remains under its custody. Revocation first clears prompts, permission requests, and timers, then independently attempts listener removal, hiding, detachment, closing, network denial, permission denial, connection cleanup, and storage cleanup. Calling `close()`, hiding the view, or setting `current=null` is not evidence of destruction; residual resources remain quarantined until actual destruction and all cleanup succeed. Main takes over retired owners before replacing a window, and the complete inventory continues to participate in debug checks and admission for new secret operations. A legitimate active prompt does not block its own input.

The fixed cleanup report contains only owner, random revoke ID, revision, status, resource count, and fixed codes. The existing ordinary vault status shows generic unavailable; logs contain no paths, URLs, or original exception text. `SECRET_CLEANUP_LIMIT.reportMilliseconds=5000` is a bounded reporting deadline, not a guarantee of atomic closure or memory erasure; after timeout the task remains held and its rejection is handled. A late success from another owner cannot overwrite the current failure. New user operations may proceed after governed cleanup succeeds, but old input authority and revoked keys do not revive. Even a successful commit must confirm cleanup of the protected surface; otherwise the vault locks and refuses to report success.

This describes T9a source and deterministic contracts, not product acceptance. It introduces no credential webpages, address copying, import, downloads, or device-host policy, and changes no KDF, AEAD, or fixed Store behavior. macOS and Windows use the same Electron lifecycle and fail-closed rules. Real product cleanup, focus/recovery, and screenshots are still required on both platforms; Node mocks or results from one platform cannot substitute.
