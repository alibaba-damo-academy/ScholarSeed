# PDFE 工作台：角色知识与修改范围

## Scope / Non-goals

PDFE 是产品经理（P）、设计师（D）、前端工程师（FE）共用的产品交付工作台。
三种角色都可以通过 Codex 等 Agent 修改代码；角色决定默认知识和任务关注点，
不代表账户权限，也不限制某一角色的编码能力。不维护角色专用产品页面或 mock 副本。

本文是角色任务与修改范围的唯一正文。产品设计理念与后续接入先读
[PDFE 概要设计](../architecture/PDFE.md)。预览装配、隔离和消息边界由
[预览架构](../architecture/preview.md)持有；需求、设计、组件、业务机制仍归原 Owner。
知识层次遵循[知识治理](../../../../docs/architecture/knowledge.md)，不在角色入口复制规范。

## Source of truth

| 任务视角 | 必要知识入口 | 任务产物与检查重点 |
| --- | --- | --- |
| P 产品经理 | 当前功能的已确认需求与验收依据；[场景目录](../../preview/catalog.ts)中的预期和限制；对应功能 Owner | 需求状态、业务流程、文案、正常/异常/边界场景；核对预期与实际，不用源码现状替代产品要求 |
| D 设计师 | [DESIGN](../../DESIGN.md)、[公开设计契约](../design/foundations.md)、[组件复用](../design/components.md)、[交互规则](../design/interaction.md)及当前场景的业务规则 | 页面布局、视觉层级、组件状态、主题、语言、键盘焦点、长内容与支持尺寸；区分稿件证据与语义推导 |
| FE 前端工程师 | [renderer](../architecture/renderer.md)、[ownership](../architecture/ownership.md)、[mock 消费契约](preview-contracts.md)、[验证规范](../quality/testing.md)及对应需求/设计 | 共享页面实现、领域场景、HTTP/SSE 消费和可回归交互；不新建平行状态投影或放宽接口/宿主边界 |

产品经理可以改样式，设计师可以补业务场景，前端也可以维护经确认的需求关联。
是否允许某次修改由明确任务范围决定，而不是由职业名称自动决定。
本次用户确认的需求范围是现有产品的完整 Mock 功能，无需另等外部 PRD。按产品全部
入口、共享 UI、领域 Owner 契约和组件 registry 核对完整性，不把已有场景目录当成
全部功能。具体语义不明时定位原 Owner 并标记待确认，不新增业务规则。场景目录登记、
执行覆盖和人工验收是不同信息。

## Current / Required / Gap / Advisory

- **current**：共享 renderer、场景目录及独立视口已有实现。三角色看到完全相同的
  功能导航和场景按钮，工作台没有角色切换；本文供 Agent 按职责和任务范围读取，
  不复制领域正文。任务上下文辅助函数不自动授予写权限；任务差异核对、实际源码
  基线捕获与完整 Agent 宿主验证仍在建设。
- **required**：每次 Agent 修改前明确角色、目标需求/页面/场景、可修改文件与行为、
  禁止范围、验证方式和停止条件。相同角色的不同任务可以有不同修改范围。
- **required**：路径允许不是语义允许。文件中混有服务、路径、持久化、权限、配置或
  全局状态逻辑时，不能因后缀是 `.tsx` 或位于 `preview/` 就视为页面/数据修改。
- **gap**：完整 Mock 功能清单、逐状态覆盖与完整产品验收尚未收口，不以角色入口存在宣称
  全部需求、全部页面状态或 Agent 范围约束已经验证。
- **advisory**：保持一个需求与一个场景的稳定身份，问题记录和截图引用这些身份，
  不因角色切换生成另一份产品事实。

## Ownership / Dependency

### 三层修改范围

| 层次 | 允许内容与前提 | 不代表允许 |
| --- | --- | --- |
| mock 样本与场景 | 本次指定样本、文案、边界数据和已有政策参数；保留实例隔离与生产 DTO | 整个 `preview/` 可改；修改服务路由、传输、准入、实例生命周期、bridge 或隔离策略 |
| 共享页面展示层 | 本次明确指定的页面/文件/交互；复用现有组件与 token；记录真实产品影响 | 整个 renderer 可改；改动全局 Store、接口语义、注册能力或所有同名组件 |
| 扩展范围与交接 | 发现依赖时报告所需 Owner、具体修改与风险，由本次任务另行确认 | 默认修改 API/DTO/SSE/IPC、main/preload/Serve、认证权限、持久化、mock 引擎、全局组件/token、依赖、构建或发布 |

Agent 不得通过预览专属 UI、直接写 Store、内部事件或永远成功的样本规避真实产品
缺陷。需要扩展范围时，停止相关动作，继续独立且已授权的工作，不能悄悄扩大权限。
生产组件缺能力按组件 Owner 扩展；不能为了保持页面任务范围而复制替代组件。

### 任务契约与交接

任务契约至少包含角色、目标需求与场景、可改文件及行为、禁止内容、验证和停止条件。
契约绑定起始源码版本与已有 dirty 状态，保护他人修改；不能把全部未提交 diff
都归为本次 Agent 的工作。后续核对需要基于该任务开始后的实际差异。

交付时分别报告：本次差异、越界或未覆盖项、需求与设计依据、mock 消费验证、
受影响真实产品验证，以及版本、场景、操作步骤、主题/语言/尺寸和截图。
知识约定不是沙箱；路径或语法检查不能证明语义没有越界，必须保留人工复核和缺口。

## Enforced by

适用的 AGENTS、实际 Owner 契约、组件/样式棘轮与原测试判据继续生效。
文档链接由 `pnpm ops ci check docs desktop` 和工作区文档检查核对。
角色任务范围工具、真实 Codex 使用和完整场景回归分别验收；不能把文档检查或
任务提示词复制成功当作角色知识已被 Agent 正确执行。

## 正反例

正例：设计师选择同一会话场景，按本次明确范围调整共享展示层，复用原组件/token，
保留产品草稿，提交具体 diff 和主题/键盘/真实产品验证结果；缺需求依据先标待确认。

反例：因为角色是前端工程师就默认改 Serve 或 IPC；因为文件在 `preview/` 就重写
隔离机制；复制任务上下文后把所有候选路径当成授权，或把 mock 通过当作真实验收。

## Update triggers

角色任务职责、修改范围、Owner 导航、任务契约或交接事实发生变化时更新本文。
领域机制变化回写原正文，角色入口只更新相关链接和读取条件。

## Stop condition

定位到本次任务的实际 Owner 和可改范围后停止扩展阅读；缺需求依据、写入授权或
真实验证前提时保留待决项，不假定角色身份、历史命令或本文授予操作权限。
