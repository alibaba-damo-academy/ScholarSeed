### Inventory and Counting Method

This index is the navigation source of truth for pages, features, and core workflows. Look up specific requirements, adoption rationales, and applicability conditions in each page's `requirements.md` and `build.md`; the overview does not redefine criteria. Inventory the four unit types separately, and ensure mappings and deduplication decisions can be traced to their sources:

| Unit | Granularity and deduplication boundary |
| --- | --- |
| Page | Count pages or standalone settings pages actually present in the target artifact. For confirmed consolidated entry points, count only the containing page while retaining the original requirements mapping. One asset may correspond to multiple pages; do not count by file count alone. |
| Feature | Inventory by distinct user goal or business capability, linked to requirement IDs and containing pages. When the same capability appears under multiple entry points, verify whether it is the same capability before deduplicating; do not automatically treat different states or special cases as separate complete features. |
| Core workflow | Record a stable ID and linked requirements for each distinguishable entry point, key action, and real terminal state. Sharing a page or evidence does not mean workflows are duplicates, and the same workflow must not be added more than once across types. |
| Special case | Define a check unit by a specific object, state or platform condition, and observable terminal state. Evidence may be reused when it overlaps with a base page or workflow, but document the scopes separately; do not remove special cases from the frozen denominator. |

For each identified unit, record its adoption status (adopted, candidate, or pending confirmation), applicability to the target version (applicable, demonstrably inapplicable, or unverified), and build status (built, partially built, or not yet built). Record run conclusions separately; do not infer them from screenshots, source code, or old results. List hidden or unverified entry points separately to avoid confusing them with proven inapplicability. If inventory completeness is unknown, the overall denominator is unknown; do not calculate a product-wide percentage. Report adoption, build, and execution coverage separately, and do not add the counts across the four types. Freeze the denominator and results for each run according to the selected evaluation type; the execution Skill defines the specific method. Historical coverage inventories mix built items, not-yet-built items, and special cases; use them only as inventory leads, not directly as the deduplicated denominator for the current package.
