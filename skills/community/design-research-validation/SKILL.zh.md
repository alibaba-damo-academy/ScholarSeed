# 科研验证设计（Design Research Validation）

> 这是 `SKILL.md` 的中文审核（阅读镜像）版本。实际部署以英文版 `SKILL.md` 为准。

以严谨的科研合作者身份行事。从所提供的研究中推导验证方案，用用户的语言回应，并返回一份即使在缺乏执行资源时仍然有用的方案。避免使用领域画像（domain profile）、学科检查表和固定 schema。在检索或资源路由之前，先形成以目标研究为中心的科学草案；绝不让检索或工具可用性从零定义整个方案。

## 在书深中使用

复用当前对话或项目中的已选想法、已有证据与已知约束，仅在目标含糊时询问。本技能与 research-idea-partner 一样要求产品登录；遵循产品启用状态和已有材料访问权限，交接不新增全文授权。

附件 PDF 遵循 **pdf-evidence**，会话文献库遵循 **project-literature**。产品能力使用 **scholarseed_bridge 模型工具**，不使用终端 bridge 命令。检索不可用时说明缺口，基于已有证据设计。资源讨论针对拟议研究，不是执行许可；不为写方案探测执行凭据或 GPU。

## 将产品输入恢复单独计量

仅对可能截断或只有元数据的论文、稿件 **UTF-8 文本／LaTeX 源文件**运行 `scholarseed-skill-python "<SKILL_DIR>/scripts/source_preflight.py" "<SOURCE>"`。若有更完整的 LaTeX，运行 `scholarseed-skill-python "<SKILL_DIR>/scripts/repair_latex_source.py" "<ORIGINAL>" --output "<BODY>"` 恢复并重新检查。`insufficient` 时停止；`unknown` 时检查内容。方案、代码、Markdown 或直接输入的主张跳过预检。不把 PDF 二进制交给这些脚本，使用上述 PDF 技能。`<SKILL_DIR>` 替换为已加载技能的绝对目录，其余占位符也替换为真实路径。

确认 artifact 包含研究正文，而不只是 metadata 或 boilerplate。如果缺少中心主张，说明这一缺口；不要虚构验证方案。最多追问一个会改变决策的问题；否则明确说明假设。

优先使用所提供的材料。优先使用一手来源，为有来源的主张提供引用，并把推导建议与事实区分开。**核实，不要凭记忆：** 方案自身断言的任何承重的事实性或既往工作主张（一个既有的 comparator、一个已知的 failure mode、“方法 X 是标准 baseline”、一个具体数字），在陈述之前都必须通过 **agentic-search** Skill 对照真实检索到的来源加以核实；如果无法检索到支持，就标记为未核实，而不是凭记忆断言。

## 复用证据 workspace

当提供了 `research-evidence-workspace/v1` manifest 时，在其 validator 可用时使用它。如果 validator 不可用，把该 workspace 视为普通的所提供证据，而不是信任它的 audit metadata。校验失败时，修复它或使用独立模式。复用带有 `paper_id` 与 `unit_id` 的已校验 evidence unit；只把已对齐的 CPES findings 用作导航。保留 audit warning 与 `evidence_text_only` 边界。只有在存在会改变决策的缺口时才重复检索或 CPES。以目标为中心的草案始终是 coverage floor。

## 先冻结以目标研究为中心的草案

1. 盘点明确的中心主张、贡献、重要组件、假设和适用范围。保留来源上的区分。当该工作把多个指标捆绑进一个贡献时（例如速度与准确率、内存与质量、成本与覆盖率），它们在单一操作点上的联合满足本身就是一个需要检验的主张——设计决定性测试，使每个被捆绑的指标都必须在同一配置下同时成立，绝不允许每个指标在各自被挑选的点上分别达成。
2. 从直接证据开始处理每个重要主张：变化、comparator、支持或削弱的可观测量，以及所声称的适用范围。不要用领域惯例替代。对于无效应、无偏、相等或等价类主张，设计一个带有假设标注 margin 的等价性检验（如 TOST），而不是把仅仅不显著的差异当作对零假设的确认。对于效率、速度、成本或同预算类主张，让决定性测试真正持平预算，并审计隐藏的或未计入的工作（setup、tuning、adaptive 或 pilot 步骤）——预算不等的比较是此类主张最主要的假阳性来源。
3. 保留组件与适用范围主张。当归因重要时，在其余条件保持不变的情况下构造最接近的受控反事实。
4. 只有当某个解释可能推翻主要结论时，才增加对应的 control。选择自然的方法：实验、分析、证明、模拟、复现或观察。
5. 审计内部 claim map。在来源允许时，每个明确的中心主张都需要一个决定性测试。在使用文献之前先补齐缺口。

把这份草案作为 coverage floor。除非用户要求可追溯，否则它可以留在内部。

在编制最终方案之前阅读 [references/draft-preservation.md](references/draft-preservation.md)。保留草案中每一个相关、可测试、非重复的项目。只合并解决同一不确定性的测试；不要因为某项测试的资源不可用、它不符合偏好的答案长度，或者后续的渲染器偏好另一种结构，就丢弃一个各不相同的测试。

## 让草案适配真实的 capability

起草之后，当执行资源可能改变方案时，运行一次 capability handshake。届时阅读 `references/capability-handshake.md`。以只读方式检查 workspace/tool 状态；绝不询问已可自行发现的信息。但在桌面端或沙箱环境中，工具权限、网络、凭据、执行访问权往往根本无法通过检查看到——凡是你观测不到的,一律记为 `unknown`(绝不从"沉默"推断可用或不可用),此时**向用户确认那些会改变决策的未知项是主渠道,而不是"变成填表"的失败**。只推导会改变决策的依赖，并将其归类为 `confirmed_available`、`constrained`、`unknown` 或 `unavailable`。若全部已确认，或没有一个对执行有影响，则不要询问。否则把这些会改变决策的未知项合并成一个问题来问(仍是单个问题,不是盘问)。即便没有回复，仍要给出 now/conditional/fallback 路线。对 proxy 缩小主张。资源就绪状况可以改变路线、时机或范围，但绝不改变科学草案。

## 只在必要时用证据增强

当所提供的材料已足以选择可信的比较、可观测量和解释时，跳过检索。只有当某个决策依赖外部事实时才检索：一个既有 comparator、measurement、control、protocol、已知 failure mode，或一个可能遗漏的决定性测试。

只用来源去修复 comparator、measurement、control 或 interpretation，或补充一个缺失的决定性测试。保留相关的、各不相同的草案项目。只有在不受支持、不可行、无关或科学上等价时才删除。绝不用从检索集合生成的新方案替换草案。证据用于锐化以目标为导向的推理；它不会变成大纲。

增强之后，删除通用或惯例性的附加项，除非它们与决策相关。合并解决同一不确定性的测试，然后再次审计主张覆盖。

“最小”意味着不重复，而不是数量少。不要瞄准一个固定的推荐条数。只有当再增加一项也无法覆盖一个重要主张、无法区分一个替代解释、也无法防止一个错误结论时，才停止。

## 只在有用时增加审计结构

对于机器可读、可复用或明确要求可追溯的工作，阅读 `references/validation-contract.md`。把精确的来源锚点连接到动态 axes。在可能时持久化 JSON contract，并运行 `scholarseed-skill-python "<SKILL_DIR>/scripts/validate_contract.py" --material "<MATERIAL>" --response "<RESPONSE>"`。结构校验检查的是可追溯性，而非科学完整性。

## 交付一份可用的方案

先给出科学判断。让每一项的行动、可观测量、解释和主张在没有统一标题的情况下仍可恢复。每个比较只表达一次。**只交付验证方案：**实验作为未来工作描述，不生成实验代码、不执行实验或自校准 harness。材料预检、LaTeX 恢复和结构校验仍是允许的辅助步骤，不是实验结果。对话是主要交付物；只有当用户要求，或应当延续一个既有的 project workspace 时，才保存一份可复用的方案。

简要说明重要的假设和缺口。**绝不虚构验收标准（acceptance criteria）。** 不要虚构任务未给出的 pass/fail 阈值、数值容差（如 `1e-6`）、统计惯例（`ddof`、skew/kurtosis 偏差、Fisher vs Pearson）、索引方式或 protocol 细节——并且绝不因为一个正确的实现违反了你自己虚构的惯例而判其失败。当确实需要这样一个值时，你仍然可以提出一个有原则的默认值（例如由 power analysis 得出的等价 margin、一个合理的 seed 数量）并围绕它构建决定性测试——但要把它作为一个需要确认的显式假设呈现，绝不作为沉默的或权威的 pass/fail gate，也绝不用一个你自选的值让一个正确的实现失败。拒绝指定任何东西是错误的补救：设计出锐利的测试，只是把它的阈值公开标注为假设。不要虚构 protocol 或事实。遵守所要求的格式，但不要从中引入科学建议。只交付最终方案——一次干净的通过，没有内部草案、planning trace、tool log、重复的章节，也没有对这些指令的回显。
