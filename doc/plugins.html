    Plugin Overview

    English · 简体中文 · Read offline

    A plugin packages a Skill and conversation cards into an installable workflow. The Skill tells the AI how to perform a task; cards display results or collect user decisions.

    Plugins are in developer preview and evolving rapidly. Future versions may introduce breaking changes.

    What Plugins Can Do

    • Organize workflows: Read authorized materials, call backend operations, handle user decisions, and deliver results.
    • Show conversation cards: Reuse public business cards or build your own interactions.
    • Reuse the official UI: Use the React runtime, controls, and Conversation components provided by ScholarSeed.
    • Deliver inspectable packages: Produce a ZIP and digest for the user to review and confirm installation.

    Plugins do not provide global tool interception, automatic approval, or arbitrary hooks into ScholarSeed events. To perform business operations, the Skill must use the available APIs; adding a button alone does not connect an operation.

    Create a Plugin

    • Through a conversation: Ask ScholarSeed to use plugin-create and describe your workflow. The AI can generate and revise the plugin.
    • Write it yourself: Follow the creation tutorial to connect a Skill, descriptor, and UI. Its example uses plain .js and ScholarSeed's React runtime: no separate Node.js installation, frontend bundler, or JSX/TypeScript compilation is required for that example. Validate and package the ZIP before delivery.

    Install and Use

    In the Skills center, choose Add skill, review the ZIP identity, version, and risks, and confirm installation. AI-generated plugins can also be delivered through an installation card; publishing a card does not mean installation succeeded.

    After installation and enabling the plugin, ask the AI to use it in a conversation. You do not need to bind it through the Skill picker first.

    Install plugins only from trusted sources. An isolated component iframe does not mean Skill scripts run in a general-purpose sandbox. Never include credentials, login caches, or environment files in a package.

    Guides

    • Create a Plugin: Generate a plugin with AI or write your first one.
    • Public Conversation Cards: Choose public slots, Conversation components, and UI controls.
    • How Plugins Run: Understand rendering, drafts, answers, updates, and historical cards.
    • Available APIs: Find frontend SDK methods, backend operations, and their actual contracts.
    • Test a Plugin: Validate a package, run a real task, and troubleshoot failures.

    Create a Plugin

    English · 简体中文 · Read offline

    Plugin Overview

    This tutorial builds paper-reading-notes. A user supplies a paper or excerpt, chooses Understand the method or Check the evidence, and receives focused notes with source locations.

    Ask the AI to Create It

    Send this in a ScholarSeed conversation:

    Use plugin-create to create a paper-reading-notes plugin. After the user supplies a paper or excerpt, show a card asking for a reading focus: Understand the method or Check the evidence. For method notes, summarize the research question, method steps, and applicable conditions. For evidence notes, summarize conclusions, supporting evidence, and limitations. Include page or paragraph locations and mark missing information as not stated. Generate the source, validate and package the ZIP, then provide an installation card.

    The AI generates the Skill, descriptor, component, and scenarios. Review the source and reports before confirming installation. To revise it, ask plugin-create for changes in the same conversation; do not create a second plugin with the same identity.

    Write It Yourself

    In a Python environment with the target ScholarSeed backend installed, obtain the required host value:

    python -c "from importlib.metadata import version; print('==' + version('scholarseed'))"

    Create these files:

    paper-reading-notes/                 # Source and package input directory
├── SKILL.md                         # Reading workflow and note requirements
├── .scholarseed-plugin.json          # Identity, compatibility, cards, and actions
└── components/
    ├── focus.js                     # Reading-focus card
    └── focus.preview.json           # Example input and submissions
request.json                        # Validation request, outside the plugin directory

    The packaging tool generates .scholarseed-package.json; do not write it by hand.

    1 SKILL.md

    Use the standard Skill format (source). This is an example inside the plugin, not a modification to ScholarSeed's bundled Skills.

    ---
name: paper-reading-notes
description: Produce method notes or evidence notes for a paper or excerpt, according to the user's chosen reading focus.
version: "0.1.0"
---

# Paper Reading Notes

1. Confirm the supplied paper or excerpt; ask for materials if missing.
2. Query component/catalog and check that reading.focus is available.
3. Use component/request to publish a reading-focus card with a question and unique request_id.
4. Wait for the answer and parse JSON {action, values} from result.answers.
5. When action is confirm, use values.focus to generate:
   - method: research question, method steps, and applicable conditions.
   - evidence: conclusions, supporting evidence, and limitations.
6. Include page or paragraph locations for every note. Mark missing information as not stated.
7. Stop on cancellation or failure. If only an abstract or excerpt is available, state that coverage limit.

    2 .scholarseed-plugin.json

    The descriptor declares identity, card entry, and input/output contracts. Replace __HOST__ with the complete output of the command above, including ==.

    {
  "schema": 2,
  "id": "paper-reading-notes",
  "version": "0.1.0",
  "host": "__HOST__",
  "skill": "SKILL.md",
  "ui": {
    "compatibility": "1.0",
    "exports": ["React", "mount", "Button"]
  },
  "capabilities": ["interaction.answer"],
  "components": [
    {
      "id": "focus",
      "slot": "reading.focus",
      "entry": "components/focus.js",
      "preview": "components/focus.preview.json",
      "input_schema": {
        "type": "object",
        "required": ["question"],
        "properties": {"question": {"type": "string"}},
        "additionalProperties": false
      },
      "output_schema": {
        "type": "object",
        "required": ["focus"],
        "properties": {"focus": {"type": "string", "enum": ["method", "evidence"]}},
        "additionalProperties": false
      },
      "actions": [
        {
          "id": "confirm",
          "capability": "interaction.answer",
          "input_schema": {
            "type": "object",
            "required": ["focus"],
            "properties": {"focus": {"type": "string", "enum": ["method", "evidence"]}},
            "additionalProperties": false
          }
        }
      ]
    }
  ],
  "configuration": []
}

    Top-Level Fields

    Field Meaning Value in this example
    schema Descriptor format The number 2.
    host Supported backend distribution version The exact queried version, prefixed by ==.
    id Unique plugin name paper-reading-notes, matching the Skill name; preserve it on updates.
    version Plugin release version 0.1.0, matching the Skill and packaging command; increment for updates.
    skill Skill entry path SKILL.md.
    ui.compatibility ScholarSeed UI API version "1.0".
    ui.exports Official exports used by the component React, mount, and Button; update when adding controls.
    capabilities Capabilities required by card actions ["interaction.answer"].
    components Cards One focus component, described below.
    configuration Optional configuration declarations [] in this example.

    Card Fields

    Field How to set it
    id Component name, unique within the plugin: focus.
    slot Name requested by the AI: reading.focus. Use two dot-separated segments; each starts with a lowercase letter and may contain digits or hyphens.
    public Defaults to false. Set true only to reference an existing public card, using its slot and no entry.
    entry Relative JavaScript path: components/focus.js.
    preview Scenario JSON path: components/focus.preview.json.
    input_schema JSON Schema for card data; defaults to an object. Declare required fields and types.
    output_schema JSON Schema for answer values; defaults to an object. Do not wrap it in {action, values}.
    actions Defaults to []. Each action has a unique id used by submit or request, a capability declared at top level, and an input_schema for its values (default object).

    For submit("confirm", {focus: "method"}), confirm is the action ID. Both the action schema and component output schema validate {focus: "method"}.

    Configuration and Validation Rules

    Each configuration declaration needs a unique key, a type (string, integer, or boolean), and a display label. It may include required and a default of the declared type. Declarations currently do not provide a settings page or value read/write API.

    Unknown descriptor fields are rejected. Resource paths use / and are relative to the plugin root; no .., absolute paths, or Windows reserved names. Schemas cannot use $ref or $dynamicRef. Revalidate after edits.

    3 components/focus.js

    The buttons submit the chosen focus. Actions are enabled only while pending. For editable forms, also handle drafts and state.

    (() => {
  const { React, mount, Button } = window.scholarseedUI;
  const create = React.createElement;

  function FocusCard({ state }) {
    const disabled = state.status !== "pending";
    const chinese = state.language.startsWith("zh");
    return create("section", { "aria-label": chinese ? "阅读重点" : "Reading focus" },
      create("p", null, state.data.question),
      create(Button, {
        disabled,
        onClick: () => window.plugin.submit("confirm", { focus: "method" })
      }, chinese ? "理解方法" : "Understand the method"),
      create(Button, {
        disabled,
        onClick: () => window.plugin.submit("confirm", { focus: "evidence" })
      }, chinese ? "核对证据" : "Check the evidence")
    );
  }

  mount(state => create(FocusCard, { state }));
})();

    The example intentionally includes both Chinese and English button labels, selected using the language supplied by ScholarSeed.

    4 components/focus.preview.json

    The descriptor's preview field connects this scenario to focus.js. data is sample input, responses simulates action responses, and submissions lists values to validate. A real conversation uses actual request data, not this file.

    {
  "data": {"question": "What would you like to focus on in this paper?"},
  "responses": {
    "confirm": {"state": "resolved", "data": {"focus": {"$input": "focus"}}}
  },
  "submissions": {
    "confirm": [{"focus": "method"}, {"focus": "evidence"}]
  }
}

    Request the Card

    After installation and enabling, the AI requests the card with these scholarseed_bridge arguments:

    {
  "capability": "component",
  "operation": "request",
  "request": {
    "request_id": "reading-focus-1",
    "slot": "reading.focus",
    "data": {
      "question": "What would you like to focus on in this paper?"
    },
    "title": "Choose a reading focus",
    "prompt": "Choose a focus to generate the corresponding reading notes."
  }
}

    When the backend returns the answer, parse {action, values} from result.answers and generate notes according to values.focus.

    Before requesting the card, preflight the slot for conflicts with enabled plugins. Use a new request_id for each new question.

    Validate and Package

    Save the inner request object above as request.json. From the plugin's parent directory, run:

    python -m service.cli.plugins validate ./paper-reading-notes/.scholarseed-plugin.json ./request.json
python -m service.cli.plugins pack ./paper-reading-notes --name paper-reading-notes --version 0.1.0 --output ./paper-reading-notes-0.1.0.zip

    After valid=true, retain the ZIP and SHA-256. Keep the ZIP outside the source directory. Increment the version and build a new package for updates.

    capabilities_unchecked means runtime capabilities have not been verified. Offline validation is not installation or execution; continue with a real end-to-end task.

    Install and Try It

    • AI-generated: Review the report on the installation card and confirm installation. published means only that the card was published.
    • Hand-written: In the Skills center, choose Add skill, select the ZIP, review the checks, and confirm installation.

    After enabling the plugin, send:

    Please use paper-reading-notes to make reading notes for the paper I just uploaded. Let me choose the reading focus first.

    Understand the method should produce the research question, method steps, and applicable conditions. Check the evidence should produce conclusions, evidence, and limitations. Both must include source locations. Follow Test a Plugin for the complete checks.

    Public Conversation Cards

    English · 简体中文 · Read offline

    Plugin Overview

    First choose what drives the card, then choose its UI. A public slot is a business entry point; Conversation components are composable UI. They are not interchangeable.

    Choose a Card

    Goal Use
    Reuse search, paper selection, authorization, or saving A public slot driven by its domain tool
    Compose an existing conversation UI Conversation components, connected to actual props and callbacks
    Collect choices for your own workflow A custom slot, data/action schemas, and component code

    Public Business Slots

    Slot Displays How it is used Implementation
    interaction.question Choices and confirmation ScholarSeed's native question flow displays it and collects answers. Choices
    display.literature-search Search summary and a button for full results Shown in the literature-result flow with the current result set. Summary
    preview.literature-results Full results, filters, pagination, and sources Open from the summary to select papers, inspect sources, or add to the library. Details
    literature.selection A paper subset Compatibility with existing literature flows; returns selected paper IDs. Choices
    literature.authorization Papers within a full-text authorization request The literature authorization flow waits for confirmation before acquiring full text. Choices
    display.literature-downloads Per-paper acquisition or import outcomes Shown after acquisition/import; users can open full text or the library. Downloads
    display.literature-delivery Save location, file conflicts, and outcomes Started with literature delivery; the user chooses and confirms a destination. Delivery
    display.literature-references References and source actions Shows cited literature, with source opening, import, and collection actions. References

    To reference a public component, set public: true, specify the existing slot and scenario file, and omit entry. Follow the actual data and actions returned by the component catalog.

    Do not fabricate public cards through generic component/request or component/display:

    • interaction.question is bound by the native question flow and has no standalone CLI question operation. For your own choices, use a custom slot from the creation tutorial.
    • Literature cards obtain real context through domain operations such as literature/result and literature/review. Inspect those operations' contracts instead of inventing their data.

    literature.outline and display.literature-review are custom slots belonging to existing plugins, not public slots.

    How a Slot Resolves to a Component

    The frontend routing lives in Component.tsx. Result cards receive content and business-operation ports; choice cards receive data/status/slot/submit. The literature.selection registration is marked legacyOnly for existing bindings and is not a general-purpose question entry for new plugins.

    Inspect all three boundaries before reuse: the public-slot list in descriptor.py, action constraints in ui.py, and frontend-to-domain mappings in ports.ts. A visible button alone does not establish a working operation.

    Example public-card reference:

    {
  "id": "results",
  "slot": "display.literature-search",
  "public": true,
  "preview": "components/results.json"
}

    Add it to components, with schemas and capability declarations matching the actual data and actions. There is no entry because ScholarSeed implements the UI. The declaration creates a reference; the literature domain tool still drives the card.

    Public Card Behavior and Examples

    The component previews retained in the Chinese edition illustrate the layout with Chinese sample content; they are not evidence of a complete English product flow. The following descriptions let English readers follow the guide without relying on those screenshots.

    • Questions and paper selection: interaction.question shows choices; literature.selection shows a selectable subset. The outer interaction owns the question and whole-turn confirmation, not the option component alone.
    • Search summary and full results: display.literature-search summarizes results; preview.literature-results contains the full list, filters, and operations. See results.json, details.json, and question.json in agentic-search/components.
    • Full-text authorization and acquisition: literature.authorization shows the requested papers; the native flow owns its buttons and authorization result. display.literature-downloads shows per-paper outcomes. Examples: authorization.json and downloads.json; paper-subset examples use scenario.json in the corresponding component directory.
    • Delivery and references: display.literature-delivery covers save destinations and conflicts. display.literature-references presents cited papers and source operations. Their UI does not independently grant download, filesystem, or library permissions.

    Conversation Components

    Read components from window.scholarseedUI.Conversation and declare Conversation in ui.exports.

    Category Current exports Your responsibility
    Research cards Choices, Results, Details, References, Downloads, Delivery, Review Real business data, operation ports, and authorization outcomes. Research cards generally take content and ports; Choices takes data/status/slot/submit.
    Prose and source content Markdown, Message, Code, Formula, Tabulation Original content, copy/open callbacks, citations, and mathematical meaning. Displaying code does not execute it.
    Artifacts Artifact, ArtifactGroup, ArtifactMenuItems, ArtifactDestination Immutable file/version identity and save/import/open operations and outcomes; groups only provide layout.
    Images ImageView, Images, ImageThumbnail Authorized URLs, asset identity, load failures, selection, and actions; components do not read arbitrary local files.
    Citations and context CitationLink, WebCitationLink, CitationSources, ConversationReference, ComposerRefChip Citation resolution, authorized previews, history snapshots, pagination, and navigation; a label is not read permission.
    Execution ExecutionProcess, ExecutionBatch, ToolExecution, ExecutionIO, ExecutionStatus, WebSearchRecord Actual turns, state, I/O, and time; unknown or interrupted results must not appear successful.
    Task support Plan, Failure, Suggestions, Attachments, FileFormatIcon Plan projection, recovery eligibility, sending, file identity, and opening; UI does not automatically resume tasks or send messages.

    Inspect catalog.composition.Conversation for input guidance and source and types for exact signatures. Exported components do not imply that all internal callbacks are available to ordinary plugins.

    UI Controls

    • Input: Button, IconButton, Checkbox, Input, Textarea, RadioGroup, Select.
    • Layout: Card and its Header, Title, Description, Content, Footer.
    • Overlays: Dialog, DropdownMenu, and their declared children.
    • Tables and feedback: Table, Alert, Badge, Progress.

    Inspect catalog.exports for exact exports and declare the top-level names you use in ui.exports. Use the official React runtime; do not bundle another React or import Desktop internals. Supply your own custom styles rather than assuming ScholarSeed generates arbitrary Tailwind classes.

    How Plugins Run

    English · 简体中文 · Read offline

    Plugin Overview

    The AI follows the Skill to issue a request. After backend validation, ScholarSeed displays a conversation card. The user's answer returns to the AI so it can continue the task.

    For the paper-reading-notes example: request reading.focus → validate the request → load focus.js → choose Understand the method → return {focus: "method"} → generate method notes.

    From Loading to Rendering

    1. The package passes installation checks and the user confirms installation and enables it. The AI discovers and uses the Skill during a real task.
    2. The AI queries the component catalog and requests an available slot. Public business cards are driven by domain tools.
    3. ScholarSeed pins the plugin and UI resource versions for the interaction. Custom components load their package entry in an isolated iframe; public cards use ScholarSeed's implementation and have no package entry.
    4. Custom components use mount(render) to receive snapshots and render into #root, including language and theme changes. Do not create a second React root or duplicate render subscriptions.

    component/request waits for an answer; component/display only displays content. A published record does not prove the business operation completed.

    Drafts and Answers

    Data Purpose Validation
    data Business input provided by ScholarSeed Component input_schema
    draft Saved UI draft Draft-saving flow; not approval or an execution result
    values Submitted values Action input_schema; interaction.answer also validates component output_schema
    {action, values} Answer envelope returned to the AI Wrapped by the backend; do not include this outer envelope in the values schema

    Use onState for the current snapshot and subsequent data, draft, status, language, slot, and theme updates. mount already connects the render subscription.

    • save(values) saves a draft without continuing the AI task. Preserve input on failure.
    • submit(actionId, values) answers the current interaction. Submit only while pending; determine completion from subsequent state.
    • Theme, language, and state updates must not clear unsaved input. An old save response must not overwrite newer edits.
    • Do not advance dependent steps after cancellation, failure, expiration, or an unknown result.

    See the frontend SDK for signatures and return values.

    Updates and Historical Cards

    Increment the Skill and descriptor versions, rebuild the ZIP and digest, and confirm the update through a new installation card or the Skills center. Preserve the old version on a slot conflict or update failure; do not silently take over another plugin.

    Historical interactions retain their original plugin version, UI resources, data, draft, and action semantics. New versions must not reinterpret old answers. Disabling prevents new bindings, but old cards still require current permission and state checks; their authorization is not permanent.

    Permission Boundaries

    Components can use only supplied data and actions that are both declared and actually connected. Their iframe has no Node, Electron, preload, or parent-document privileges. It is not an arbitrary file, HTTP, or command proxy.

    Skill backend calls and frontend SDK calls are separate interfaces. Declaring a capability neither connects a handler nor grants business permissions. This protocol has no global event interception, tool rewriting, or automatic approval API.

    Available APIs

    English · 简体中文 · Read offline

    Plugin Overview

    scholarseed-bridge is ScholarSeed's backend CLI for agents to inspect resources, manage literature, and display conversation cards. Skills use this CLI; card interfaces use the frontend SDK.

    Use the CLI

    Inside ScholarSeed's agent execution environment, use scholarseed-bridge <capability> <operation> --json '<request>':

    scholarseed-bridge history list --json '{"limit":5}'
scholarseed-bridge component catalog --json '{"include_ui":true}'
scholarseed-bridge component preflight --json '{"slots":["reading.focus"]}'

    The CLI uses the current session's project and authorization. Inspect parameters with:

    scholarseed-bridge --help
scholarseed-bridge component request --help

    AI can also call the scholarseed_bridge model tool using {capability, operation, request}. JSON examples below use that envelope; the CLI's --json accepts only its inner request.

    Inspect the Actual Contract

    In a Python environment with the matching backend installed, run:

    python -m service.cli.plugins describe

    This returns the descriptor format, component SDK, and request definitions. Follow the target backend's output when developing or updating a plugin. See Write It Yourself for the host value.

    Frontend SDK

    Method Result Purpose
    window.plugin.onState(callback) Unsubscribe function Current snapshot and later state updates; unsubscribe on unmount.
    window.plugin.setCopyContent({text, markdown?}) Promise with registration result Register copyable card text; does not write the system clipboard.
    window.plugin.save(values) Promise with {state, revision} Save a JSON draft without continuing the AI task.
    window.plugin.submit(actionId, values) void Submit an answer; determine completion from subsequent state.
    window.plugin.request(actionId, values) Promise with the operation result Invoke a declared operation with a handler in the current context.
    window.scholarseedUI.mount(render) Unmount function Mount React UI and synchronize state, language, and theme.
    window.scholarseedUI.useCopyContent(text) React Hook Add the current component's text to the card's copy content.

    Ordinary custom cards currently connect plugin-call only to skills.list and navigation.skills. Full text, classifications, and saving in literature cards use domain-specific ports. Copying names such as literature.read or navigation.open does not grant those operations to an ordinary card.

    Register Copyable Card Content

    Register text after UI state updates. When copying a message, ScholarSeed merges turn prose and card content in order. Public cards generate this text from business data; do not register it again.

    Inside mount(), official Conversation.Choices, Results, Details, References, Downloads, Delivery, and Review components automatically register text. Compositions merge their content. Collapsed review sections, citations, checks, and questions remain included. Artifacts retain titles and paths; their file contents are not automatically read.

    Markdown, Message, Code, Formula, and Artifact also register automatically. Code retains its full source even when collapsed; formulas retain LaTeX, descriptions, and annotations. Tabulation requires copyText or invalidSource and does not infer data from table DOM.

    For custom rendering, call window.scholarseedUI.useCopyContent(text) inside a component and declare useCopyContent in ui.exports. The Hook combines text from components and re-registers it after saved state updates; registration failures appear inside the card. Do not combine this Hook with direct setCopyContent() calls that replace the entire card's text.

    const { React, mount } = window.scholarseedUI;

function Notes({ state }) {
  const [error, setError] = React.useState("");
  const focus = state.draft?.focus ?? "evidence";
  React.useEffect(() => {
    let current = true;
    window.plugin.setCopyContent({
      text: `Reading focus: ${focus === "method" ? "Understand the method" : "Check the evidence"}`
    }).then(() => {
      if (current) setError("");
    }).catch(() => {
      if (current) setError("Copy content could not be saved");
    });
    return () => { current = false; };
  }, [focus, state.revision]);
  return React.createElement("p", { role: error ? "status" : undefined }, error || focus);
}

mount(state => React.createElement(Notes, { state }));

    text is required. Include headings, body, current choices, and citations or links that should be preserved, but not action buttons such as Submit or Expand. Optional markdown may retain source; copying currently uses text, and HTML is not accepted. Registration is limited to 64 KiB and also subject to the total message-size limit.

    Wait for save() to finish, then register text using the new state delivered through onState. Draft updates invalidate old text; registrations against an old revision are rejected. Registered text persists with the card's session binding, so copying historical cards does not rerun their iframe. Cards without text explicitly indicate the omission. Registration neither advances the AI nor grants clipboard read/write permission.

    Discover Components and Slots

    Query components and official UI exports:

    {"capability":"component","operation":"catalog","request":{"include_ui":true}}

    The result includes current components, UI exports, and the composition catalog. Read-only preflight checks custom slots for conflicts:

    {"capability":"component","operation":"preflight","request":{"slots":["reading.focus"]}}

    Preflight checks only conflicts. Installation and enabling validate again.

    Discover Backend Operations

    List operations and inspect their request contract:

    {"capability":"contract","operation":"list","request":{}}

    {"capability":"contract","operation":"describe","request":{"target_capability":"literature","target_operation":"read"}}

    Current CLI Operations

    Names in this table follow scholarseed-bridge.

    Commands and operations Purpose Effects and precautions
    history list / search / read List sessions, search messages, and read more content Read only currently authorized history.
    resource list / read List or read current-project resources Read-only; continue large-file reads using returned pagination.
    resource import Import published artifacts or session files into project resources Writes resources; confirm files and destination first.
    pdf list / status / read / search / library / annotations Inspect PDFs, preparation state, text, evidence windows, and annotations Read authorized content; returns citation identity and page numbers.
    pdf prepare Prepare PDF text and index Starts preparation; use status for progress.
    pdf materialize Write PDF content to a destination Creates files and records; confirm the destination.
    pdf register-card Register a paper_card Writes structured literature evidence and its version.
    literature list / read / annotations / receipt Read literature, text, annotations, and full-text authorization receipts receipt reports the actual authorized and acquired full-text scope for this turn.
    literature authorize Request full-text permission Shows candidate papers and waits for user confirmation.
    literature result / review Show search-result or review-workflow cards Presents checkpoint results, collects choices, or confirms an outline.
    literature acquire Obtain authorized candidates' open full text Downloads and manages files; returns per-paper outcomes.
    literature ingest / import Import downloads or session files into the literature library Writes library entries and associates the current project; import follows an explicit user instruction.
    literature delivery Present the full-text saving workflow Pins a delivery batch, then saves or imports according to later user choices.
    literature collection.list / tag.list List collections or tags Collections belong to the current project; tags are shared globally.
    literature collection.create / collection.update Create, rename, or move collections Modifies the current project's collection structure.
    literature tag.create / tag.update Create or rename tags Changes global tags; renaming affects every project using them.
    literature collection.delete / tag.delete Delete collections or tags Returns affected associations first; deletion requires user confirmation.
    literature organize Add or remove collection/tag associations Changes selected literature entries' associations.
    search run Execute product search Makes external requests and registers new results. Do not automatically retry: another call runs another search.
    search browser Internal browser callback for search Used by existing search tasks; plugins use search run.
    artifact publish Publish generated file artifacts Registers files and pinned versions for opening or saving.
    plan get Read the current plan Returns the plan, step IDs, and revision.
    plan write / structure / action Write plans, change structure, or record execution actions Changes plan state; supply the current revision and operation request ID.
    task activate Activate task identity Changes the current turn's binding; called by the Skill launcher.
    display-card Show a business card Creates a recoverable conversation card; takes --json directly.
    component catalog / preflight Inspect components, exports, or slot conflicts Read-only.
    component request / display Request interaction or display a custom card Creates a card; request waits for an answer, display only displays content.

    Source and Types

    Use a source revision matching the target ScholarSeed version. These repository-relative links work in a public checkout without access to a private code host:

    • Descriptor and schema, offline tools.
    • Official UI exports, component catalog.
    • SDK types, Conversation exports.
    • Action handlers, research-card ports.
    • CLI commands, backend operation registry and effects.

    When an upgrade is incompatible, update the plugin and rerun checks. Do not merely widen the host range or skip validation.

    English · 简体中文 · Read offline

    Plugin Overview

    Install and Complete a First Conversation

    Prepare paper-reading-notes-0.1.0.zip and a paper you are authorized to use.

    1. Open ScholarSeed and go to the Skills center → Add skill, then select the ZIP.
    2. Review the plugin name, version, and check results, and confirm installation.
    3. Find paper-reading-notes in your skills list and enable it. For an AI-generated plugin, you can instead confirm installation on its conversation card.
    4. Open your conversation, upload the paper or paste an excerpt, and send the prompt below.
    5. When the reading-focus card appears, choose Understand the method. Verify that notes cover the research question, method steps, and applicable conditions, with source locations.
    6. Start another task and choose Check the evidence. Verify that notes instead cover conclusions, supporting evidence, and limitations. Missing information must be marked as not stated.

    Example prompt:

    Please use paper-reading-notes to make reading notes for the paper I just uploaded. Let me choose the reading focus first.

    No prior binding through the Skill picker is required. If no card appears, check that the plugin is enabled and the tool history contains a component/request call.

    Check UI and Updates

    For a custom card, call setCopyContent() and use the message's copy button. Paste into a text editor and verify the order of prose, cards, and subsequent conclusions, including choices, citations, and links. Switch conversations and return: copying history must still include the card. Register new copy content after editing a draft; do not copy stale choices. Missing card text must be explicitly indicated when none is registered.

    • UI: Light/dark themes, narrow windows, keyboard use, long text, and errors.
    • State: Re-rendering preserves edits; old save responses do not overwrite new input; cancellation does not continue the task.
    • Updates: A new package, digest, and installation confirmation; slot conflicts do not take over other plugins; failures preserve the old version.
    • Historical cards: Restore their pinned version and recheck current permissions.
    • Platforms: Verify affected installation and runtime behavior separately on macOS and Windows.
